## 3. 整改总原则

### 3.1 数据和权限不变量

整改完成后必须同时满足：

1. repository 查询本身带 `workspace_id + owner/user scope`，不得先查出跨空间数据再由 service 过滤。
2. trusted header 只能由已验证的可信代理注入；浏览器自报的用户、角色、部门和 workspace 永远不可信。
3. 同一 logical job attempt 在任意时刻最多只有一个有效 lease owner；失去 lease 的 worker 不能继续提交结果或执行新副作用。
4. 同一用户对同一消息最多存在一条当前反馈；点赞改点踩是覆盖，不是并存。
5. audit 的 applied、failed、rejected 都必须留下记录；配置写成功但审计缺失属于失败。
6. SSE 只有在收到合法 `done` 后才能进入 `completed`；断流、半帧、非法帧、客户端停止和上游错误必须落入不同且准确的状态。
7. 默认 Compose 配置必须可启动并完成最小会话链路，测试 fixture 不能通过覆盖错误默认值掩盖部署缺陷。
8. 所有新增 `/api/v1` 错误统一返回 `{code, message, details, request_id}`。

### 3.2 兼容与迁移原则

- 所有数据库修改使用 expand/contract；本轮只允许增加表、列、索引或兼容视图，不直接删除已提交结构。
- 旧 `audit_logs`、旧 feedback 数据如果需要迁移，必须提供可重复运行的 backfill 和数量/hash 校验。
- 数据迁移由独立 migration role 执行；BFF/worker 运行角色不得自动获得 DDL 权限。
- 旧 `/api/chat*` 和 `/api/admin/*` 继续工作；新实现通过 feature flag 灰度。
- 不允许通过 HTTP 200、空内容或 fallback 文本掩盖权限、数据库、迁移或上游故障。

## 5. FIX-P0-WORKER-01：修复 lease 心跳、脑裂和重复副作用

### 5.1 对应原工作包

- F-03：PostgreSQL、Alembic、Repository 与最小作业框架。
- 原计划停止条件：同一 logical attempt 被两个 worker 同时执行副作用。

### 5.2 根因

- `JobRunner._heartbeat_loop()` 执行 heartbeat UPDATE 后未提交事务，session 关闭时更新被回滚。
- heartbeat/complete/fail 没有同时校验 `lease_owner + attempt/fencing token`。
- worker 失去 lease 后只停止心跳，正在运行的 handler 没有收到取消信号。
- 当前测试只覆盖“两个 worker 同时领取一个短任务”，没有覆盖 handler 运行时间超过 lease 的场景。

### 5.3 允许修改范围

- `map-business-backend/app/repositories/jobs.py`
- `map-business-backend/app/workers/job_runner.py`
- `map-business-backend/app/workers/main.py`
- job model/migration（仅新增 fencing/lease 所需兼容字段或索引）
- `map-business-backend/tests/integration/test_job_runner.py`
- worker README、metrics/log 定义

禁止修改会话、反馈、审计业务语义；禁止引入 Redis/Kafka。

### 5.4 必须实现

1. heartbeat 在独立短事务中提交；失败时显式 rollback，并记录结构化错误。
2. heartbeat 条件至少包含：`job_id`、`status=running`、当前 `lease_owner`、当前 `attempt` 或单调递增 fencing token。
3. complete/fail 也必须使用同样的 owner/fencing 条件；过期 worker 不得覆盖新 worker 的结果。
4. reclaim 必须在带锁事务内进行，不能批量无条件重置所有 expired job 后递归领取。
5. runner 为 handler 提供 lease-lost/cancel signal；handler 在每个副作用安全点前检查。
6. 外部副作用 handler 使用稳定 idempotency key；重放相同 logical attempt 不产生第二次外部动作。
7. heartbeat 间隔小于 lease 的 1/3，加入合理 jitter；数据库短暂超时不能静默继续执行到 lease 过期。
8. 日志包含 `job_id, workspace_id, worker_id, attempt/fence, lease_expires_at`，不得包含 payload secret。

### 5.5 必须新增测试

- 1 秒 lease + 运行 3 秒 handler + 两 worker：副作用计数严格为 1。
- heartbeat 提交后，另一数据库 session 可观察到延长后的 lease。
- worker A 失去 lease、worker B 回收后，A 的 complete/fail 返回 ownership lost，不能改终态。
- worker kill 后不再 heartbeat，lease 到期可被 B 回收。
- heartbeat 数据库超时、session rollback、进程 SIGTERM 三条路径。
- retry handler 重放相同 idempotency key，外部 fake counter 仍为 1。

### 5.6 验收标准

- 上述测试使用真实 PostgreSQL，至少连续运行 20 次无偶发双执行。
- job 状态机和 attempt/fencing 变化可从数据库查询验证。
- `uv run pytest tests/integration/test_job_runner.py -q` 全绿且无未等待协程/资源泄漏告警。
- 任何 stale worker 都不能成功 heartbeat、complete、fail 或提交副作用。
- 提供 worker drain、应用回滚和运行中 job 清点说明。

## 6. FIX-P0-AUTH-01：可信身份边界和管理员授权 fail-closed

### 6.1 对应原工作包

- F-04：统一身份、workspace context、请求/会话 ID。

### 6.2 根因

- `trusted_proxy_required` 默认 false；trusted_header 模式可直接信任浏览器 Header。
- 任意调用方可自报 `X-User-Roles: platform_admin` 并通过管理写权限。
- `ServicePrincipal` 只有数据类，没有实际服务身份校验、audience/scope 验证和 delegation 边界。
- Compose/.env/README 未固定安全模式和启动失败条件。

### 6.3 允许修改范围

- BFF `app/core/identity.py`、`app/api/deps.py`、`app/main.py`、`app/settings.py`
- 服务身份/权限/error middleware 新文件
- `.env.example`、`docker-compose.yml`、BFF README
- BFF 身份与跨 workspace 测试
- map_core 内部身份消费契约（只做 additive 校验）

### 6.4 必须实现

1. `MAP_AUTH_MODE=trusted_header` 时必须配置可信代理验证机制；缺少 secret/reference 或代理来源配置时启动失败。
2. 共享 secret 比较使用常量时间函数；secret 不得写日志、响应、trace、audit。
3. `MAP_ENV=prod` 下禁止 dev 模式，也禁止关闭 trusted proxy 验证。
4. 浏览器发送的 roles/workspace/subject 只有在请求通过代理身份验证后才读取。
5. admin 权限由统一 permission service 判定；不得在 router 中散落字符串判断。
6. 实现 `ServicePrincipal` 解析和校验：service name、audience、scopes、token rotation reference；用户代理执行同时携带独立 actor context。
7. identity middleware 只解析一次 principal；后续 service 只依赖 principal，不重新读任意 Header。
8. 401/403 使用标准错误 envelope，并带 BFF 生成的 request_id。

### 6.5 必须新增测试

- 无代理凭据、错误凭据、伪造 platform_admin：401，管理状态不变且无成功审计。
- 正确代理凭据 + 普通用户访问管理写：403。
- 正确代理凭据 + platform_admin：允许。
- prod + dev、prod + trusted_header 但验证关闭/凭据空：应用启动失败。
- service token audience/scope 错误：401/403；浏览器 token 访问 `/internal/v1`：拒绝。
- secret fuzz：日志、错误响应、audit、OTel attributes 中均找不到凭据。
- 跨 workspace 读取/写入返回 403/404，且 repository SQL 自带 workspace predicate。

### 6.6 验收标准

- 原验收中的伪造管理员请求由 200 变为 401。
- 所有 admin 写路由通过统一授权依赖；OpenAPI 自动枚举测试证明无遗漏。
- 默认 Compose dev 可启动；prod 配置不安全时明确拒绝启动。
- BFF/core/Mongo/OTel 的 request/session/workspace ID 契约测试继续全绿。

## 8. FIX-P1-CONV-01：重建会话流状态机、SSE 缓冲、停止和恢复

### 8.1 对应原工作包

- R1-CONV-01：会话与消息最小持久化。

### 8.2 当前缺陷

1. BFF 调用 `parse_sse_frames(text)` 后丢弃 `remaining`，任意半帧会丢事件。
2. bytes 每 chunk 独立 decode，UTF-8 多字节字符跨 chunk 时可能被替换损坏。
3. 未收到 `done` 也会进入 `completed`。
4. `POST /messages/{id}:stop` 只改数据库，实际 core 流仍继续，之后可能覆盖为 completed。
5. 注释声称存在 reconciler，但代码中没有实现。
6. create conversation 未接入 `Idempotency-Key`。
7. request_id 重放查询只限制 workspace，未限制 conversation/owner；已知 request_id 可能返回同空间其他用户的消息。
8. 新增 `message.started` 事件不符合冻结的 SSE 事件集合。
9. 前端仍使用旧 `/api/chat*` 和 React 内存历史，刷新不能恢复新会话。
10. message 表缺少计划要求的 `stream_error`、`fallback_used` 等事实字段。

### 8.3 允许修改范围

- BFF conversation schema/model/migration/repository/service/router
- BFF SSE parser 和 stream execution registry
- BFF job reconciler handler
- 业务前端 `api/client.ts`、chat reducer/controller、conversation feature
- map_core 仅允许 additive ID/meta 修复
- 会话 unit/integration/contract/frontend 测试

### 8.4 必须实现

1. 使用单个跨 chunk buffer 和增量 UTF-8 decoder；每次解析后保存 `remaining`。
2. 支持 LF/CRLF、多行 data、多个 frame、半帧、单字节分片、UTF-8 字符中间分片。
3. 明确状态机：`pending -> streaming -> completed|failed|stopped`；只有合法 `done` 可 completed。
4. 上游 EOF 无 done、非法 done、解析错误、core error、客户端 abort 分别记录稳定 error code。
5. `stream_error` 和 `fallback_used` 独立持久化；fallback 不能覆盖原错误事实。
6. 连接活动表由 app 生命周期管理；stop 设置 abort_event/取消下游请求，并使用状态/version 条件更新防止终态被覆盖。
7. 实现 reconciler：超过阈值的 streaming 消息标记 `failed/interrupted`，幂等且可观测。
8. request_id 重放必须绑定 `workspace_id + owner_user_id + conversation_id`；跨用户/跨会话不可返回已有内容。
9. 并发相同 request_id 时捕获唯一冲突并安全 re-query；不能向客户端暴露 500，也不能留下孤儿 user message。
10. create conversation 使用公共 IdempotencyService；同键同 body 重放，同键不同 body 返回 409 标准错误。
11. 使用冻结的 `start/meta/content_delta/done/error`；message IDs 放入 `start` 或 `meta.phase`。
12. 前端通过 feature flag 接入新 conversation API，支持创建、刷新恢复、加载当前会话、停止和错误状态展示。

### 8.5 必须新增测试

- 对完整 SSE 按每个字节位置拆分；最终事件、内容、状态完全一致。
- 中文 UTF-8 字符按每个字节拆分，内容无 `�`。
- EOF 无 done、error 后 done、非法 JSON、重复 done、断流、客户端 abort。
- stop 与 done 竞态运行至少 50 次：只允许一个终态，stop 后 core 不继续产生副作用。
- BFF crash 后 reconciler 把 stale streaming 标为 interrupted。
- 两并发相同 request_id：只有一对 user/assistant message。
- 用户 B 使用用户 A 的 request_id：404/403，绝不返回 A 内容。
- create conversation Idempotency-Key replay/conflict。
- 旧 chat API contract snapshot 无删除、无字段类型变化。
- 前端刷新后恢复已完成/failed/stopped 消息。

### 8.6 验收标准

- 原 E-03 故障注入变为内容完整、状态 completed、事件顺序正确。
- 无 done 永不 completed；stopped 不能再次变 completed。

## 10. FIX-P1-AUDIT-01：按不可抵赖审计要求重建写入链路

### 10.1 对应原工作包

- R1-AUDIT-01：配置写入统一化与不可抵赖审计。

### 10.2 当前实现为何不能增量打补丁即宣称完成

当前 `audit_logs` 只记录成功后完整 before/after，且 `except Exception` 吞掉审计失败。它缺少原计划的 mutation 状态机、applied/failed/rejected、JSON Patch、hash chain、原子写、reconciler、secret redaction、并发 expected hash 和数据库权限约束。因此整改应以原计划模型为目标重新建立链路，同时保留旧表兼容读取。

### 10.3 允许修改范围

- BFF config service/repository/store/audit model/migration/router
- 所有 `/api/admin/*` 写路由（仅改为统一 service 调用）
- 审计查询 API、校验脚本和 BFF tests
- 管理前端 audit 页面仅在对应 UI 工作包中接入

### 10.4 必须实现

1. 新建 `config_audit_events` 和 `config_mutations`，字段与原计划一致。
2. 所有 AdminState 写必须通过 `ConfigMutationService`；禁止 router 直接 `store.update(lambda ...)`。
3. 写流程严格为：pending mutation -> expected hash compare -> 临时文件写/fsync/atomic rename -> applied/failed audit -> mutation 终态。
4. 进程在每个崩溃点重启后，reconciler 根据 before/target/current hash 追加 recovered 事件。
5. applied、failed、rejected 都写审计；审计失败不得被吞掉并返回成功。
6. 使用稳定 JSON Patch；list 通过业务 key 对齐，排序变化不产生整表 delete/add。
7. 审计前统一 redaction：headers/env_refs 仅记录键名和变更标记；token、authorization、cookie、password、secret 不出现值。
8. `entry_hash` 串联前条 hash；并发写在事务内锁定链尾，不能产生分叉。
9. 提供 `scripts/verify_audit_chain.py` 或等价命令，返回第一条断点。
10. 应用角色对审计表只有 insert/select，无 update/delete；迁移角色单独授权。
11. AdminState 解析失败必须保留坏文件并返回明确错误，绝不回退默认后覆盖。
12. API 使用 `/api/v1/admin/audit-events`，支持原计划筛选；旧 `/api/admin/audit-logs` 可做只读兼容 facade。
13. audit 查询从 repository 开始带 workspace scope；只读审计员可读但不能写配置。

### 10.5 必须新增测试

- 自动枚举每个现有 Admin PUT/POST/PATCH/DELETE，参数化验证 actor、resource、status、diff、hash。
- operator/body/Header 伪造不影响 actor。
- state file 无权限、磁盘满/写失败、临时文件失败、fsync 失败、rename 失败：API 失败且有 failed audit，原文件完整。
- 并发相同 expected hash 只有一个成功，另一个 409。
- 在 pending 后、rename 后、audit insert 前分别模拟进程崩溃，reconciler 正确恢复。
- 手工篡改审计行后校验定位第一条断点。
- secrets/headers/env_refs fuzz 不泄漏。
- 跨 workspace 查询和 audit viewer 权限。
- 坏 AdminState 文件不会被默认值覆盖。

### 10.6 验收标准

- 所有管理写均经统一 mutation service，无 router 直接 store.update。
- applied/failed/rejected 的自动化证据齐全；hash chain 校验通过。
- 任一文件写失败不产生半文件，任一审计失败不返回伪成功。
- 数据库权限测试证明应用角色不能 UPDATE/DELETE audit event。
- 旧 audit 数据迁移/兼容策略和回滚说明完整。
