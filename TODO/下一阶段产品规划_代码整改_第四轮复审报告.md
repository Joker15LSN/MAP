## 5. 阻断问题

## R4-P0-01：EffectGuard 的 dispatch-before-call 崩溃窗口仍会永久漏动作

### 证据与根因

相关位置：

- `map-business-backend/app/workers/job_runner.py:180-203`
- `map-business-backend/app/workers/job_runner.py:271-298`
- `map-business-backend/tests/integration/test_effect_protocol_windows.py:97-121`
- `map-business-backend/tests/integration/test_effect_protocol_windows.py:164-176`

当前协议先把 effect 从 `pending` 提交为 `dispatching`，再调用 provider。两者之间不是原子操作：

```text
commit dispatching
    <--- 进程可在此死亡；provider 尚未收到请求
call provider
```

恢复时，`begin_dispatch()` 看到 `dispatching` 就把它转为 `uncertain`，禁止重放。对于“请求可能已发出”的窗口，这是合理的 at-most-once fail-closed；但对于“dispatching 已提交、请求尚未发出”的窗口，它会永久漏执行。

现有 W2 测试在 `record_intent()` 后立即 crash，此时 effect 仍是 `pending`，重试当然可以执行 provider。测试没有覆盖 `begin_dispatch()` 已提交后的剩余区间，因而“四窗口连续 20 次动作计数恒 1”的结论是测试注入点造成的假闭环。

### 风险

- 通知、付款、审批、订阅、消息投递可能从未发生；
- job/effect 虽不会伪报 succeeded，但只能人工处理 uncertain，自动交付语义仍未闭环；
- provider callable 不强制接收 idempotency key，代码层无法证明外部系统按同一键去重；
- 并发调用遇到已有 `dispatching` 也会立即置 uncertain，可能把仍存活的第一调用变成失败。

### 整改方向

若产品验收继续要求每个崩溃窗口动作最终严格为 1，必须引入 provider 侧幂等/查询能力，不能仅靠本地数据库状态推断：

1. 把 provider 接口改为强制接收稳定 idempotency key；禁止闭包自行决定是否使用 key；
2. provider/fake provider 按 key 保存调用事实和确认结果；重试同一 key 不产生第二个动作；
3. 对 `dispatching` 恢复先按 key 查询 provider：已确认则落 `delivered`，明确未收到则用同一 key 重发，未知才进入 `uncertain`；
4. effect 行增加 dispatch token/owner/attempt/lease 或等价并发围栏，不能由第二个存活调用立即把第一调用标记 uncertain；
5. 若目标 provider 不支持幂等或查询，只能明确把契约改成 at-most-once + possible-zero，并由产品负责人修改第三轮验收标准；不得继续宣称 exactly-once 或“四窗口动作恒 1”。

### 整改验收标准

- 新增真实 PostgreSQL crash point：`begin_dispatch()` 提交后、provider callable 第一行前；
- W1 intent 前、W2 intent 后、W2b dispatch 后/provider 前、W3 provider 动作后/ack 前、W4 ack 后/job complete 前，每个连续运行 20 次；
- 对要求 exactly-once 的 provider，上述每个窗口最终服务端动作事实数严格为 1，不能为 0 或 2；
- provider timeout 后按 idempotency key 可查询确认的，恢复为 delivered；无法确认的保持 uncertain，job 不得 succeeded；
- 两个并发 runner 使用同一 key 时，只有一个外部动作，存活调用不被另一个调用提前置 uncertain；
- 测试统计必须来自 fake provider 的服务端持久事实，不能只统计进程内 list。

## R4-P1-01：E2E 的 worker kill 场景没有杀死真实 lease owner

### 证据与根因

位置：`e2e/run_e2e.py:1283-1347`。

脚本当前顺序是：

1. 手工插入 `status='running'`、`attempt=1`、`lease_owner='dead-worker'` 的 job；
2. `docker kill` 真实 worker 容器；
3. 重新启动 worker；
4. 等待 synthetic dead-worker lease 过期，真实 worker 第一次认领时 attempt 变为 2。

被 kill 的容器从未持有这条 job 的 lease，也没有开始 handler。该测试只证明“启动后的 worker 能回收一条预制过期 running 行”，没有证明：

- worker 在 handler 处理中被 kill；
- attempt 1 的事务/副作用处于哪个崩溃窗口；
- stale worker 的提交被 fencing 拒绝；
- takeover 后外部动作或业务写恰好一次。

`takeover_attempt=2` 只是插入值 1 后的一次 claim 自增，不能证明“接管恰好一次”。

### 整改方向

1. E2E 创建一条真实 queued job，由真实 worker 认领；
2. 轮询数据库，确认 `status=running`、`attempt=1`、`lease_owner` 等于即将 kill 的 worker ID；
3. handler 使用仅 E2E 启用的可控 barrier/延迟，确保进程停在指定崩溃窗口；
4. kill 同一个 lease owner 容器，再等待 lease 过期并启动新 owner；
5. 对 message reconcile，验证旧 worker 零提交、新 worker只提交一次；对 effect handler，使用支持 idempotency key 的 fake provider验证服务端动作事实数为 1；
6. artifact 记录 killed container ID、old/new lease owner、attempt 序列、崩溃点和 provider action count。

### 整改验收标准

- kill 前数据库中的 `lease_owner` 必须与被 kill worker 的 `MAP_WORKER_ID` 一致；
- kill 发生时 handler 已越过明确 barrier，不允许预制 `dead-worker` 行替代真实认领；
- takeover 后 attempt 精确从 1 变 2，old owner 的 late complete/fail 均被拒绝；
- 业务写/外部动作事实数严格为 1，旧 worker 提交数为 0；
- 连续 10 次全新 volume 运行无 0/2 次动作；
- 将 scenario 名称保留为 `worker_kill_lease_takeover` 的前提，是上述真实 kill 已实现；否则必须诚实改名为 `expired_lease_reclaim`。

## R4-P2-02：dependency advisory 未校验且通过 shell 字符串拼接

### 证据

位置：

- `scripts/load_dependency_exceptions.py:80-103`
- `scripts/dependency_audit.sh:39-48`
- `scripts/dependency_audit.sh:72-75`

loader 只校验 advisory 非空和不重复，不限制空白、换行、`--ignore-vuln`、分号等字符。audit 脚本再把 advisory 拼入字符串 `IGNORE_ARGS`，最终进入容器 `sh -c`。

当前登记表为空，所以本次依赖审计没有实际被绕过；但未来只要新增一条例外，就可能违反“一条登记 = 一个 ignore 参数”，甚至用 `; true` 掩盖 pip-audit 失败。

### 整改与验收标准

- advisory 必须是单个合法 ID，至少禁止空白、控制字符和 shell 元字符；支持的 CVE/GHSA/PYSEC 格式应显式列出并测试；
- host shell 使用数组保存 `--ignore-vuln` 参数，禁止拼接命令字符串；
- 容器内如需 `sh -c` 安装工具，应把 audit 参数通过 `"$@"` 位置参数传入，而非插入脚本文本；
- 恶意值（空格、换行、`;`、`#`、`$()`、额外 `--ignore-vuln`）全部由 loader fail closed；
- 自动化证明一条例外只产生一个 argv，两条例外产生两个 argv；
- 自动化注入 pip-audit 非零退出时，即使例外字符串恶意也不得把 gate 变为 0。

1. **Config mutation**：继续保持 target hash/context 在 rename 前提交；exact hash 规则不变；
2. **审计筛选**：继续保持 action/time/actor/resource/status/request_id + workspace predicate；
3. **OpenAPI allowlist**：继续保持零 diff 也先校验 allowlist；
4. **PG roles**：继续使用 `%I/%L` 安全引用和 fresh-volume 特殊字符测试；
5. **探针身份边界**：`/health`、`/ready` 可无身份访问，业务路由在 trusted_header 下仍 401；readiness UUID+code 双条件不变；
6. **Release gate 主体**：21 个步骤当前全部通过，不得通过删除步骤解决新失败；
7. **R1-EVAL/灰度边界**：R1-EVAL 未实现继续显式 501，不创建假 case；conversation feature flag 默认策略不得被本轮整改扩大。

## 9. 第五轮最终验收门槛

第五轮复验至少同时满足：

1. R4-P0-01、R4-P1-01 全部关闭，P2 无不受控例外；
2. EffectGuard 新增 dispatch-after-commit/provider-before-call 窗口，连续 20 次动作事实数严格为 1；
3. provider idempotency key 由接口强制传入并由 fake provider 服务端持久事实验证；
4. E2E kill 的 worker 必须是数据库当前 lease owner，kill 时 handler 已进入明确 barrier；
5. takeover 后 old owner 零提交、attempt 1→2、业务写/外部动作严格一次；
6. browser E2E 对未预期 console/page/network error fail closed，最终 unexpected 集合为空；
7. 供应链 loader 拒绝多 token/命令元字符 advisory，audit 参数使用安全 argv；
8. BFF/map_core/观测后端 Ruff + pytest、两个前端 test/build、bundle、pip-audit、两个 production npm audit 全 exit 0；
9. `git diff --check <第四轮基线>..HEAD`、Compose config 全绿，产品代码工作区干净；
10. PR E2E 在最终 HEAD 通过；full E2E 连续两次全新 volume 通过；
11. gate/E2E artifact 自带 git SHA、tree、dirty 状态、时间、exit code，质量记录与实际提交数一致；
12. R1-EVAL 501 与 conversation feature flag 的尚未实施/灰度状态继续显式保留。

任一门槛未满足，验收结论继续保持“不通过”。
