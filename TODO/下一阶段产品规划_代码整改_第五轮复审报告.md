### 3.2 effect 围栏真实 PostgreSQL 最小重放

重放顺序：

1. owner A 以 attempt 1 获得 120 秒 dispatch lease；
2. 在 A lease 仍有效时，owner B 以 attempt 2 调用 `adopt_dispatch()`；
3. B 接管成功，数据库当前 owner 已是 B；
4. owner A 的迟到失败路径调用 `mark_uncertain()`。

实测输出：

```text
begin = proceed
owner_b_adopted_while_a_lease_live = True
before_stale_write = (dispatching, owner-B, 2)
after_stale_owner_write = (uncertain, owner-B, 2, late owner-A timeout)
```

说明 owner/attempt/lease 没有作为 UPDATE 的 compare-and-set 条件。数据库保留了 B 的 owner 字段，却接受了 A 的终态写，形成自相矛盾状态。

### 3.3 两个真实 `run_effect_once()` 的协议级重放

进一步使用两个并发调用重放：A 已进入 provider；B 在 A lease 有效时接管并停在 provider 发送前；随后 A 超时，最后放行 B 的服务端动作。

实测：

```text
owner A -> EffectUncertainError(provider timeout)
owner A 迟到后 ledger -> uncertain / owner-B / attempt=2
owner B -> EffectUncertainError(ack lost the fenced transition)
provider_action_facts = 1
final ledger = uncertain / owner-B / attempt=2
```

外部动作事实已经是 1，但两个 worker 都报告失败且 ledger 为 uncertain。这不只是字段或文档问题，而是会造成“外部已执行、内部永久不确定”的生产语义错误。

## 5. 必须整改的问题

## R5-P0-01：effect owner/attempt/lease 没有形成数据库并发围栏

### 证据位置

- `map-business-backend/app/workers/job_runner.py:272-303`：`adopt_dispatch()` 只以 workspace/key/status 为条件；
- `map-business-backend/app/workers/job_runner.py:305-341`：`ack_effect()`、`mark_uncertain()` 不接收 owner/attempt/token；
- `map-business-backend/app/workers/job_runner.py:417-456`：先读取 status/lease，再执行无 token UPDATE，存在 TOCTOU；
- `map-business-backend/app/workers/job_runner.py:526-552`：旧 dispatcher 的 exception/false response 会直接调用无围栏 `mark_uncertain()`；
- `map-business-backend/tests/integration/test_effect_protocol_windows.py`：已有并发测试依赖 provider key 去重，没有注入“旧 owner 迟到写覆盖新 owner”的交错顺序。

### 根因

新增列目前只承担观测用途，没有参与所有权校验：

```sql
WHERE workspace_id = ?
  AND effect_key = ?
  AND status = 'dispatching'
```

任何看到 `dispatching` 的调用都能改 owner，也能把行推进 `delivered` 或 `uncertain`。注释所称“loser 重新读取”“只有当前 lease attempt 能推进”没有被 SQL rowcount 语义保证。

### 风险

- stale worker 可以覆盖已接管 worker 的进行中状态；
- provider 已完成动作时 ledger 仍可能终止在 uncertain；
- 两个 job attempt 都失败，人工重试又因 uncertain 被禁止，形成永久人工处置；
- `provider_action_count=1` 只能证明外部去重，不能证明 job/effect 状态机恰好一次闭环；
- 现有 20 轮 crash-window 测试没有覆盖该确定性交错，继续重复也无法发现问题。

### 整改方向

1. 为每次 dispatch generation 建立不可复用的 fencing token。可新增 `dispatch_token UUID`，或把当前 owner/attempt 与单调 generation/version 组合成等价 token；
2. `begin_dispatch()` 成功时返回 token，而不是只返回字符串；后续 owner 变更和终态写必须携带该 token；
3. `adopt_dispatch()` 使用单条原子 CAS：至少比较 observed token/owner/attempt/status；正常接管还必须比较数据库时间下的 lease 过期条件。CAS rowcount=0 的调用不得继续发送，必须重新解析 provider/ledger 事实；
4. `mark_uncertain()` 只允许当前 generation 写入，并返回是否成功。旧 owner 失去 CAS 时不能宣称 uncertain，必须读取当前状态；
5. provider 已按 key 返回 confirmed 时，可由专门的对账路径把事实推进到 delivered，但该路径必须定义清晰的单调优先级，不能与 stale uncertain 互相覆盖；
6. 所有 read-then-write 分支必须把所读 generation 带入 UPDATE，不能只读 `lease_alive` 后再按 status 更新；
7. 对 provider exception、false response、query unknown、lease expiry、re-adoption 和 ack 每个路径统一使用同一 fencing API，禁止遗漏某个异常分支。

### 整改验收标准

- 把第五轮最小反例固化为真实 PostgreSQL 测试：A lease 有效时 B 不得无 CAS 接管；一旦 B 合法接管，A 的 `mark_uncertain`/ack 必须 rowcount=0；
- 固化协议级 barrier 测试：A 在 provider 内、B 已合法接管、A 迟到 timeout、B 完成动作；最终 `provider_action_count=1`、ledger=`delivered`，不得是 uncertain，不能两个 attempt 都失败；
- 对 owner A/B 的关键交错至少连续运行 20 轮；每轮服务端事实数=1、最终状态=delivered、旧 owner 终态提交数=0；
- 两个并发 recovery 同时看到 provider query=False 时，只允许一个 generation 获得发送权；loser 必须重新查询；
- provider query=None 且旧 lease 活跃时不能写 uncertain；lease 过期后，也只有持有当前 observed generation 的原子 CAS 能写 uncertain；
- W1/W2/W2b/W3/W4 各 20 轮继续全部通过，不能为修复并发围栏破坏 crash recovery；
- migration 如新增 token/version，必须有 upgrade/downgrade、旧行兼容、唯一 head 和 fresh database 测试；
- 文档和类型注释必须与实际 SQL predicate 一致，不得只写“fenced”而没有 rowcount 证明。

## R5-P1-01：disconnect 清理验收被未 await coroutine 短路，gate 假绿

### 证据位置

`map-business-backend/tests/integration/test_conversation_stream.py:498-509`：

```python
async def _cleanup_done() -> bool:
    return core.closed.is_set() and registry.active_count() == 0

while not _cleanup_done():
    ...
```

`_cleanup_done()` 返回 coroutine 对象；对象 truthy，因此 `not coroutine` 为 False，循环一次也不执行。pytest 日志已明确输出：

```text
RuntimeWarning: coroutine ... _cleanup_done was never awaited
303 passed, 135 warnings
```

单独加入 `-W error::RuntimeWarning -W error::pytest.PytestUnraisableExceptionWarning` 后该测试 exit 1。

### 风险

- `core.closed` 和 `registry.active_count()==0` 没有得到测试验证；
- 原本用于降低 flaky 的 30 秒等待实际失效；
- release gate 把未处理 coroutine 当作 warning，产生“303 passed”的假绿证据；
- 该错误位于第四轮修改文件中，不能归为无关存量 warning。

### 整改方向

1. predicate 不执行异步操作，应改为普通 `def _cleanup_done()`，或直接复用已存在的 `_wait_until()`；不要仅在循环前加一次状态断言；
2. 给等待 helper 增加超时时的状态诊断，同时保证 predicate 在每轮实际执行；
3. BFF gate 至少把 `RuntimeWarning` 和 `pytest.PytestUnraisableExceptionWarning` 升格为错误；Alembic 的明确 DeprecationWarning 可单独治理，不能以此为由放行 unawaited coroutine；
4. 检查第四轮新增测试中的其他 coroutine predicate，确认没有同类模式。

### 整改验收标准

- 将 `core.closed=False` 或 registry 保持非零时，测试必须等到超时并失败；不能立即通过；
- 正常断开场景在预算内达到 `core.closed=True`、registry=0、message=`stopped`；
- 该测试以 warnings-as-errors 单独运行 exit 0；
- BFF 全套 pytest 在 gate 中不得出现 `coroutine was never awaited`、`PytestUnraisableExceptionWarning` 或未处理 async task；
- release gate 的 BFF 命令本身固化上述 warning policy，并新增一次失败复现测试证明未 await coroutine 会让 gate 非零。

- 最终 full E2E 的四个 unexpected 数组仍必须为空，且不存在过期 quarantine。

- 中文 docs-only 修改可能让 final mode误拒绝；
- 更严重的是 dirty product run 只有旧 HEAD/tree，没有 working-tree 内容哈希，无法自证测试对象；
- 修复报告中的“同一工作树”仍依赖人工叙述，不满足不可变交付证据标准。

### 整改方向

1. gate 与 E2E 统一使用一个经过测试的 source-control snapshot 实现，避免 shell/Python 两套解析漂移；
2. 使用 NUL 分隔格式，例如 `git -c core.quotepath=false status --porcelain=v1 -z`，以 bytes/NUL 解析；正确处理首行、空格、中文、rename 的双路径和 untracked 文件；禁止对 porcelain 整体 `.strip()` 后按固定列切片；
3. docs/product 分类只对解析后的真实 repo-relative path 执行；分类规则必须集中维护；
4. pre-commit artifact 如允许 dirty，应额外记录 staged/unstaged/untracked 内容 manifest 或 diff hash，并明确标为非 final；
5. 正式证据必须在产品修复提交后执行 final mode，让 commit SHA/tree 本身完整描述产品代码；允许 docs-only dirty 时，必须准确列出真实路径。

### 整改验收标准

- parser 单测至少覆盖：首行 tracked 修改、普通 untracked、路径含空格、中文 Markdown、rename、删除、同时 staged+unstaged；输出必须与真实路径逐字节一致；
- 仅中文 `TODO/*.md` dirty 时，`docs_only_dirty=true`，两个 final mode 都允许继续；任一产品文件 dirty 时必须在执行测试前 exit 非零；
- E2E artifact 不再出现 `2e/...` 或带引号的 `\\344...` 路径；gate/E2E 对同一工作树生成完全一致的 dirty path 集合和分类；
- 完成全部修复并提交后，在同一不可变 HEAD 执行 `RELEASE_GATE_FINAL=1` 和 `MAP_E2E_FINAL=1`；artifact 必须记录 `final_mode=true`、产品 tree clean、准确 SHA/tree/branch/UTC；
- gate summary 每步 command/exit/log hash 齐全；E2E report 的 source-control 字段可脱离质量记录独立验证；
- 质量记录只引用 artifact 内 SHA，不再用“同一工作树”叙述代替机器证据。

## 9. 最终判定

第四轮整改**不能验收通过**，也不建议按当前状态直接组织最终提交。

最严重的问题不是 provider 侧重复动作，而是本地并发围栏没有真正执行：旧 owner 能把新 owner 的有效 dispatch 覆盖为 uncertain。第五轮已经在真实 PostgreSQL 和两个真实 `run_effect_once()` 层级分别复现，属于确定性 P0。与此同时，disconnect 清理测试被 coroutine 写法短路，说明常规 `303 passed` 不能作为该路径成立的证据。

下一智能体应先完成 1 个 P0、1 个 P1、2 个 P2，再提交并在不可变 HEAD 上重建 gate/E2E artifact。真实 owner kill 和供应链 argv 安全可以保留现有实现，但必须随最终 HEAD 回归。只有第 8 节全部满足，才允许宣称第四轮整改关闭并进入合并/发布阶段。
