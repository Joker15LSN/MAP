## 4. 阻断问题

## R3-P0-01：worker 的 fenced transaction 与外部副作用语义仍未闭环

### 问题 A：生产 handler 绕过 runner session 独立提交

位置：

- `map-business-backend/app/workers/main.py:46-55`
- `map-business-backend/app/services/message_reconciler.py:34-67`

`_message_reconcile_handler(job, session)` 明明收到 runner 提供的 session，却丢弃它并重新调用 `get_session_factory()`；`reconcile_stale_streaming_messages()` 再打开新 session 并自行 `commit()`。

这会破坏 runner 已实现的核心保证：handler 数据写与 fenced `complete()` 应在同一事务提交；lease 丢失时 runner rollback 应撤销 handler 写。当前 message reconciler 可以先独立提交消息终态，随后 heartbeat 失败或 complete 围栏失败，runner 已无法回滚该写入。

虽然该 UPDATE 当前具有幂等条件，重复执行通常不会二次修改终态，但它仍违反整改标准“失去 lease 的 worker 不能继续提交结果或执行新副作用”，并给后续 handler 留下错误示范。

### 问题 B：EffectGuard 是 at-most-once claim，不是 exactly-once effect

位置：

- `map-business-backend/app/workers/job_runner.py:80-117`
- `map-business-backend/tests/integration/test_job_lease_fencing.py:530-602`

`claim_effect()` 在真正外部动作之前提交一条 idempotency record。若进程在 record commit 后、外部调用前崩溃，重试看到记录已存在，便跳过动作并把 job 标记成功。

复审使用真实 PostgreSQL 注入该窗口，得到：

```text
job_status=succeeded attempts=2 ledger=True external_effect_count=0
```

现有测试只覆盖：

- claim 前崩溃；
- 外部动作后崩溃。

它没有覆盖最关键的 claim 后、动作前窗口，因而“exactly-once”命名和交付结论不成立。

### 风险

- 通知、付款、审批、订阅、消息投递等后续 handler 可能永久漏执行；
- 数据库显示 job succeeded，运营侧无法自动识别动作从未发生；
- production handler 的独立事务使 lease fencing 只保护 job 行，不保护真实业务写。

### 整改方向

1. `message_reconcile` 必须使用 runner 传入的 session，禁止自行 commit；业务写和 fenced complete 在一个事务中提交。
2. handler 在查询/UPDATE 前及任何不可逆动作前检查 `ctx.lease_ok`；必要时把 owner/attempt fence 下沉到业务 UPDATE。
3. 不得再把“先写已完成 ledger、后执行动作”称为 exactly-once。选择以下可证明方案之一：
   - transactional outbox：事务内写 effect intent，独立 relay 调用外部系统，收到确认后标记 delivered；
   - 外部系统支持稳定 idempotency key：每次重试都调用同一 key，只有拿到确认后才把本地 effect 标记 delivered；
   - 对不支持幂等的外部系统，明确采用 at-most-once 并让 `uncertain` 成为可观测终态，禁止伪报 succeeded。
4. side-effect job 启动前强制校验非空 idempotency key；`None` 不得成为跨 job 共用键。

### 验收标准

- heartbeat 失败/lease 过期发生在 message reconcile UPDATE 前后时，stale worker 的消息写入数为 0，job 可被新 owner 回收；
- handler 业务写与 `Job.status=succeeded` 同事务，要么同时提交，要么同时回滚；
- crash before intent、after intent before effect、after effect before ack、after ack before job complete 四个窗口均有真实 PostgreSQL 测试；
- 每个窗口连续运行 20 次：外部 fake provider 的最终动作计数严格为 1，不允许 0 或 2；
- provider 返回 unknown/timeout 时 job 不得伪报 succeeded，必须保持 retryable/uncertain 可观测状态。

## R3-P1-01：config mutation 的真实崩溃恢复会误记 applied

### 现状

位置：

- `map-business-backend/app/services/config_mutation.py:277-288`
- `map-business-backend/app/services/config_mutation.py:373-400`
- `map-business-backend/app/services/config_mutation.py:510-524`
- `map-business-backend/tests/integration/test_audit_chain.py:230-240`

实际写序列为：

1. pending mutation 只保存 `expected_hash` 并提交；
2. `update_with_hash()` 在一次调用中计算新状态并完成 atomic rename；
3. rename 返回后才计算 `after_hash`；
4. audit event 与 mutation 的 `target_hash=after_hash` 一起提交。

因此，若进程在步骤 2 rename 成功后、步骤 4 提交前崩溃，数据库里的 pending mutation 必然是 `target_hash=NULL`。

reconciler 当前规则是：只要 `current_hash != expected_hash` 且 target_hash 为空，就记为 applied。若该 mutation 根本没有写文件，而另一实例完成了无关写入，也会被误记 applied；若该 mutation写过 B、之后别人写成 C，recovered event 又会错误地把 C 的 hash 归到前一个 mutation。

现有“after rename”测试直接手工构造 `target_hash=current`，但生产路径在该崩溃点不可能已经持久化该值；另一个测试甚至把任何 `current != expected` 直接断言为 applied。测试没有复现真实代码时序。

### 风险

- failed/rejected 尝试被记录为 applied；
- audit after_hash 指向其他操作者的配置；
- 不可抵赖审计出现错误归因，chain 本身仍能 verify OK，造成“完整但不真实”的审计证据。

### 整改方向

1. 把 mutation 分为 prepare 与 apply：先纯计算 target state/hash 和脱敏 patch；
2. 在 rename 前提交 `expected_hash + target_hash + 原 actor/workspace/request/resource/action 上下文`；
3. 再执行 expected-hash CAS + atomic rename；
4. reconciler 只允许 `current==target` 判 applied、`current==expected` 判 no-write；其他 hash 一律 `UNKNOWN_STATE`，不得猜测 applied；
5. 测试必须在真实 `apply_mutation()` 内注入 crash point，禁止只手工造一条理想 mutation 行。

### 验收标准

- pending 后崩溃：recovered failed/NO_WRITE；
- target 持久化后、rename 前崩溃：failed/NO_WRITE；
- rename 后、audit 前崩溃：applied，after_hash 精确等于 target_hash；
- crash 后另一实例先完成无关写：原 mutation 为 failed/UNKNOWN_STATE，不得 applied；
- recovered event 保留原 workspace、actor、request_id 和 resource/action；
- 每个 crash point 连续 20 次，chain verify 通过且状态/归因完全一致。

## R3-P1-02：Compose E2E 仍未达到 browser 与安全/故障矩阵要求

### 现状

位置：`e2e/run_e2e.py:55-65`、`e2e/run_e2e.py:400-799`。

当前 `SERVICES` 不包含 `frontend-service`，runner 使用 Python `urllib/http.client` 直接调用 BFF，没有浏览器或 Playwright。它证明了真实 BFF/core/PostgreSQL/Mongo/OTel 的后端链路，但不能证明：

- conversation feature flag 开启后的真实 UI；
- 浏览器创建、SSE 渲染、刷新恢复、停止、反馈和撤回；
- frontend API client 的 request/session/workspace/idempotency header 传递；
- trusted_header 安全模式、跨用户、跨 workspace、service identity；
- BFF/PostgreSQL 短暂故障、worker kill/lease takeover。

ID 校验也只在 Mongo `request_records` 断言 request_id、trace_id、session_id；没有断言 workspace/conversation/message ID 全链路一致。报告中 Mongo LLM calls=0，也说明该观测集合并未覆盖实际 fake LLM 调用。

此外，`.github/workflows/ci.yml` 只运行 release gate，不运行该 E2E；真实跨服务链路可回归而 CI 仍全绿。

### 整改方向

1. Compose E2E 启动 frontend，设置 `VITE_MAP_CONVERSATIONS_ENABLED=true`；
2. 用 Playwright/等价浏览器从页面完成 create -> stream -> reload -> stop -> feedback -> withdraw；
3. 增加 secure Compose profile，至少覆盖 forged admin、member 403、service audience/scope、cross-user/workspace；
4. 增加 BFF restart、PostgreSQL interruption、worker kill + lease takeover；
5. 在 PG/Mongo/Jaeger 中断言 request/session/workspace/conversation/message/trace ID；
6. 把稳定子集纳入 CI；完整故障矩阵可拆 nightly，但 PR 至少运行 browser happy path + identity boundary。

### 验收标准

- browser 真实访问前端，而不是直接 HTTP 调 BFF；
- reload 后同一 conversation/message/feedback 状态恢复；
- secure mode 下 forged admin 恒 401，cross-user/workspace 无数据泄漏；
- BFF/PG/worker 故障后终态、重试、lease 和副作用计数符合契约；
- CI 对 browser E2E 回归会失败并上传 report、compose logs、trace IDs；
- 连续两次干净 volume 运行全绿，且不读取开发者 `.env` 或现有 volume。

## R3-P2-03：PostgreSQL role 初始化脚本未安全引用变量

位置：`map-business-backend/db/init/01-roles.sh:22-52`。

用户名以裸 SQL identifier 拼接，密码以单引号字符串拼接。合法但包含引号/特殊字符的生产密码会导致 SQL 语法错误；非简单用户名也会失败。脚本注释又要求生产覆盖默认密码，因此该路径必须支持真实 secret，而不能只支持当前测试值。

### 验收标准

- 使用 psql variable + `format('%I', identifier)` / `format('%L', literal)` 或等价安全引用；
- 限制/校验角色名格式，错误时 fail closed 且不打印 password；
- fresh-volume 测试至少覆盖含空格、单引号、美元符号的密码；
- 日志、docker inspect 之外的测试 artifact 不出现 secret；
- 既有 volume 的手工迁移步骤与回滚说明同步更新。

## R3-P2-04：供应链例外到期规则未被脚本执行，审计工具未固定

当前无生产依赖漏洞，DOMPurify 3.4.13 的修复有效；本问题是 gate 的未来可执行性：

- `SECURITY_EXCEPTIONS.md` 声称例外过期会直接失败；
- `scripts/dependency_audit.sh` 不解析该文档或到期日，只依赖手工维护 `IGNORE_ARGS`；
- `pip-audit` 每次在浮动的 `python:3.13-slim` 中执行未固定版本的 `pip install pip-audit`，相同代码未来可能因工具/base image 漂移得到不同结果。

### 验收标准

- 使用机器可读例外文件，脚本验证 advisory、owner、批准人、工单和 expires；过期例外必须有自动化失败测试；
- 固定 pip-audit 版本并优先固定容器 digest；升级通过独立依赖更新提交；
- 当前空例外继续保持，任何新增 ignore 参数必须与有效例外一一对应；
- artifact 记录 audit tool 版本、base image digest 和被审计 lockfile hash。
