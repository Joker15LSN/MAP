## 5. 阻断问题与整改验收标准

### R2-P0-01：过期 lease 的 worker 仍能提交任务终态

**证据**

- `app/repositories/jobs.py:138-145` 的 `complete` 只校验 id、running、owner、attempt，没有校验 lease 尚未过期；
- `app/repositories/jobs.py:173-180` 的 `fail` 同样缺少 expiry 条件；
- 独立复演中，强制 lease 过期 5 秒后，旧 worker 的 `complete` 返回 True，并写入 `SUCCEEDED`；
- 现有测试只覆盖“B 已回收导致 owner/attempt 改变”后的 stale write，没有覆盖“lease 已过期但 B 尚未来得及 claim”的窗口。

**风险**

旧 worker 可在租约失效后、fence 尚未递增前提交结果或随事务提交 handler 数据库副作用，破坏 exactly-once 和脑裂停止条件。

**整改方向**

1. heartbeat、complete、fail 的 fencing 条件统一包含 `lease_expires_at >= database_now()`；时间判断优先使用数据库时间，避免 worker 时钟漂移；
2. complete/fail 返回 ownership lost 时，显式 rollback handler 会话，禁止顺带提交 handler 在同一 transaction 中产生的副作用；
3. handler 的外部副作用必须经过可持久化 idempotency/outbox adapter，不能只靠 `ContextVar` 文档约定或进程内 `set`；
4. handler 返回后、complete 前再检查 lease/cancel，并保证检查与状态提交在同一数据库事务内；
5. 对显式配置的 heartbeat interval 做启动校验，任何值都必须严格小于 lease/3。

**整改验收标准**

- 新增测试：lease 过期、无人回收时，原 owner 的 heartbeat/complete/fail 全部返回 False；
- 新增测试：handler 已产生未提交 DB 写后 lease 过期，complete 失败且 handler DB 写被 rollback；
- 在 expiry 前后 ±100ms 的竞争窗口至少运行 100 次，旧 worker 成功终态数恒为 0；
- 1 秒 lease + 3 秒 handler + 两 worker + heartbeat timeout 用例连续 20 次副作用严格为 1；
- retry/kill/SIGTERM/DB timeout 四类场景使用持久化 idempotency 事实源，进程重启后仍不重复。

### R2-P0-02：ServicePrincipal 可自报 scope，且与用户代理认证错误耦合

**证据**

- `app/main.py:133-144` 对 trusted_header 模式的所有路径先强制解析用户 principal，包括 `/internal/v1/*`；
- `app/core/service_identity.py:54-58` 在验证一个全局共享 token 后，直接信任调用方提供的 `X-Service-Name/Audience/Scopes`；
- 合法 service token 单独请求在安全模式返回 401；额外伪造用户代理凭据后变成 200；
- 同一 token 自报 `internal.ping,admin.write,anything` 后仍返回 200，响应确认这些 scope 被接受；
- 现有 service identity 测试只在 `AuthMode.DEV` 下验证 happy path，绕开了生产身份中间件。

**风险**

任一 service token 持有者可冒充其他服务并自行扩权；内部 API 在实际 trusted_header 模式下又无法按独立服务身份正常调用。随着内部写接口增加会形成直接横向越权。

**整改方向**

1. `/internal/v1/*` 从用户 principal 中间件中明确分流，只接受 ServicePrincipal；浏览器 API 只接受 RequestPrincipal；
2. token 必须绑定 service name、audience、scopes 和 rotation key id：可使用签名 JWT/mTLS，或服务端 token reference -> metadata 映射；
3. `X-Service-*` 只能作为签名声明的传输/调试信息，不得决定授权；
4. rotation 使用引用/key id，不在环境中用一个逗号分隔的全局万能 secret 给所有服务；
5. 服务代理用户执行时使用独立 actor/delegated-user context，不得要求伪造一套普通用户 Header 才能进入 internal route。

**整改验收标准**

- trusted_header/prod 配置下，合法 service credential 单独调用授权 internal route 为 200；
- 修改 name/audience/scope Header 不改变 credential 固有声明，超出授权恒为 403；
- service A credential 冒充 service B、增加 admin scope、错误 audience 均失败；
- 用户代理 credential、浏览器 bearer、两类 credential 混用均不能绕过边界；
- rotation 前后双 key 窗口、撤销旧 key、日志/trace/audit secret fuzz 全绿。

### R2-P1-01：StreamRegistry 在真正消费上游流之前已注销

**证据**

- `app/services/conversation_service.py:156-159` 注册 stream；
- `app/services/conversation_service.py:160-184` 的 `finally` 只包住“创建 async generator 对象”，因此在 `async for chunk in chunks` 之前立即执行 `unregister`；
- 独立复演中，已经产出 `start` 和第一个 `content_delta` 时 registry 为 0，stop signal 找不到 message；
- 现有 50 次 stop race 测试只断言数据库终态是 stopped/completed，没有断言 registry 命中、上游 `aclose` 或 stop 后副作用计数。

**风险**

stop 只能抢占数据库终态，真实 core 仍继续推理、调用工具和产生费用/副作用；这正是整改指南要求关闭的原始缺陷。

**整改方向**

1. registry 生命周期覆盖从注册到整个 `async for`、parser close、finalize 的全过程；仅在最外层 finally 注销；
2. registry 保存 abort event 和实际 stream task/response close handle，stop 时主动 cancel/close，而不是只等待下一个 chunk；
3. stop endpoint 必须检查 registry abort 结果并记录结构化日志/metric；跨进程部署需说明同实例路由或共享取消机制；
4. 客户端 disconnect、显式 stop、上游 done/error 的清理路径统一，保证无 registry 泄漏。

**整改验收标准**

- mid-stream `active_count==1`，stop 返回时 `abort=True`，上游 generator 的 finally/close 标记已触发；
- stop 后 fake core 的工具/外部副作用计数不再增加；
- 50 次 stop/done race 不仅终态唯一，还必须断言 losing side 不继续执行；
- client disconnect、core hang、无新 chunk 情况都能在超时内取消；
- 流结束后 registry 恒为 0，且无 pending task/unhandled cancellation。

### R2-P1-02：7 个管理写绕过 ConfigMutationService，审计失败仍被吞掉

**证据**

`app/api/admin_assets.py` 仍有 7 处直接写：

- line 98：business agent create；
- line 122：business agent update；
- line 193、211、302：MCP server 写；
- line 322、428：skill 写。

这些路由使用 `admin_write_guard`。`app/services/audit.py:81-97` 只追加旧 `AuditLog`，并在失败时捕获异常后继续返回成功。独立调用 MCP 写得到 200，新 `config_audit_events` 增量为 0，旧 `audit_logs` 增量为 1。

`tests/integration/test_config_audit.py:80-130` 虽枚举了 OpenAPI 写路径，但只真正请求了少数 model/flow/basic/release 路由，未对枚举出的每条路径参数化执行，因此没有发现上述遗漏。

**整改方向**

1. 删除管理路由内所有直接 `store.update`；统一调用公开的 `ConfigMutationService.apply_mutation`；
2. `admin_write_guard` 只负责授权/上下文，不再承担一个可吞异常的第二套 legacy 写审计；
3. legacy `/api/admin/audit-logs` 只读 facade 从新事件映射或明确只显示旧历史，不允许新写继续落旧表；
4. 自动枚举测试必须为每个写 operation 生成/维护合法 payload fixture 并真实执行，不能只统计路径数量。

**整改验收标准**

- `rg 'store\.update\(' app/api/admin_*.py` 为 0；
- 每个 Admin PUT/POST/PATCH/DELETE 成功、失败、拒绝均产生且只产生对应的新审计事件；
- 强制 audit flush/commit 失败时 API 不得 2xx，mutation 留 pending 并可恢复；
- 参数化测试断言 OpenAPI 全部管理写 operation 与 fixture 集合一一相等，新增路由未补 fixture 时 CI 失败；
- 旧 `audit_logs` 不再接受新产品写入。

### R2-P1-03：审计 hash chain 可并发分叉，恢复事件 hash 与校验器不一致

**证据**

- `app/services/config_mutation.py:267-275` 和 `447-454` 使用“查询最后一行 `FOR UPDATE`”锁链尾；该方式不会锁住将要插入的新尾节点；
- 独立两事务复演中，A、B 两事件均引用同一个 anchor，产生两个 child；
- `audit_record_payload` 把 `error_message` 计入 hash，但 `ConfigAuditEvent` 表/模型没有该列；
- bad-state reconciler 以非空 error_message 计算并存储 hash，校验器只能用 `error_message=None` 重算，复演结果 `stored_hash_matches_verifier=False`；
- 当前测试只验证 entry_hash 唯一，不验证每个节点只有一个后继，也没有在 bad-state recovered 后立即执行 verifier。

**整改方向**

1. 使用每 workspace/全局唯一的 chain-head 行并 `SELECT FOR UPDATE`，或事务级 advisory lock；更新 head 与插入 event 同事务完成；
2. 数据库增加可验证的单链不变量（sequence/ordinal、唯一 predecessor 或 head version），不能只靠应用层“查最后一行”；
3. hash canonical 字段必须全部持久化；要么新增脱敏 `error_message` 列，要么从 canonical 集合删除该字段，writer/verifier/reconciler 只使用一个 schema；
4. verifier 按链关系/ordinal 遍历，不只依赖 `created_at,id` 排序；
5. 给已有分叉/坏 hash 数据提供检测与修复/隔离策略，禁止静默重算覆盖历史。

**整改验收标准**

- 100 个并发 append 重复至少 20 轮，最终只有一个 genesis、每个非尾节点恰有一个 child、verify 恒为 OK；
- pending-before-write、after-rename、bad-file 三类 recovery 后立即 verify 通过；
- 任意 hash-relevant 字段修改都能定位第一断点；非 hash 字段必须明确列出；
- 测试主动制造共同 predecessor 时数据库约束或事务锁阻止第二个分支提交。

### R2-P1-04：Compose 应用角色是 superuser，append-only 权限约束无效

**证据**

- `docker-compose.yml:7-10` 用 `POSTGRES_USER=map` 初始化官方 PostgreSQL；该 bootstrap 用户默认是 superuser；
- 实际查询：`map|rolsuper=t|rolcreaterole=t|rolcreatedb=t`；
- `db/init/01-roles.sql:22-25` 又给 map 默认授予所有表的 SELECT/INSERT/UPDATE/DELETE；
- `7c0b1d3e5f6a_config_audit_tables.py` 创建审计表后没有显式 REVOKE UPDATE/DELETE；
- 现有权限测试临时创建另一个受限角色，只证明测试角色受限，不证明 Compose 实际应用 DSN 受限。

**风险**

应用被攻陷或出现缺陷时可以修改、删除审计事件、DDL 和角色；“append-only”“迁移角色与业务角色分离”均只是文档描述。

**整改方向**

1. 使用独立 bootstrap/admin、migrator、app 三个角色；backend/worker DSN 指向非 superuser app；
2. fresh init 结束前明确 `ALTER ROLE app NOSUPERUSER NOCREATEDB NOCREATEROLE`；生产密码不得复用默认 `map`；
3. audit migration 显式 revoke app 的 UPDATE/DELETE/TRUNCATE，并只 grant SELECT/INSERT；schema owner 保持 migrator；
4. default privileges 对普通表和 audit 表分开处理，不能先全授再遗漏 revoke；
5. 权限测试必须直接使用 Compose 中 backend/worker 的真实 DSN。

**整改验收标准**

- fresh Compose 查询 app role：`rolsuper=false, rolcreaterole=false, rolcreatedb=false`；
- 用 backend DSN 对 audit 表 UPDATE/DELETE/TRUNCATE/ALTER 全部失败，SELECT/INSERT 按契约成功；
- 用 migrator DSN 空库 upgrade/downgrade/upgrade 成功；用 app DSN 执行 DDL 失败；
- 角色/密码通过 secret/ref 注入，仓库默认值只允许显式本地 profile。

### R2-P1-05：交付的 E2E 不是指南要求的跨服务 E2E

**证据**

`tests/e2e/test_minimal_flow.py:1-9` 明确说明：

- browser 用 httpx ASGITransport 模拟；
- map_core 用 `FakeCore` 模拟；
- Mongo projection out of scope；
- 使用既有 pytest 数据库 fixture，而不是 Compose 全新 volume。

这与整改指南 13.2/13.3 的 browser -> BFF -> core -> PostgreSQL/Mongo、ID 一致性、故障、全新 Compose 一键执行要求直接冲突。map_core golden 测试只能证明 core 内部契约，不能替代 BFF/core 边界、Mongo 投影、OTel 传播和真实网络取消行为。

**整改方向**

1. 保留现有测试但改名为 BFF integration；
2. 新建 Compose E2E profile/runner，启动独立 PostgreSQL/Mongo、真实 BFF、真实 map_core；
3. 使用浏览器测试或至少从已构建前端发起真实 HTTP/SSE，禁止 ASGI in-process transport；
4. 使用 deterministic fake LLM/tool adapter 注入 map_core 内部，而不是把整个 core 替换掉；
5. 验证 request/session/workspace/conversation/message/task/trace IDs 到 PostgreSQL、Mongo、OTel 的一致性；
6. 加入 BFF/core restart、断流、重复请求、worker kill、stop/abort、audit failure。

**整改验收标准**

- 一条命令在随机 Compose project/全新 volumes 上完成并清理；不依赖本机 15432 已有数据；
- 测试网络拓扑中存在真实 BFF 和 map_core 容器，Mongo 至少校验对应 trace/event；
- 报告输出服务版本、request IDs、数据库计数、最终状态和 audit chain 结果；
- fake 只位于 LLM/外部工具边界，不能替换被验收服务。

## 6. P2 质量与完整性问题

### R2-P2-01：观测前端测试退出 1，测试矩阵也未达到 happy/empty/error

**证据**

- `ToolCallDetailDrawer.tsx:498-512` 在 payload 结构不完整时直接读取 `main_flow_logs_page.items` / `cbb_logs_page.items`；
- loading 用例 resolve `{rows,total}` 后触发 TypeError，Vitest 报 1 unhandled error、exit 1；
- `ToolCallDetailDrawer.test.tsx` 没有完整 happy payload 测试；

- 因此不满足“每个 panel 至少 happy、empty、error”。

**整改与验收**

- 对可选 page 使用 schema normalization/optional fallback，不在 loading/partial payload 阶段解引用；
- 用真实 API contract fixture 覆盖完整 happy；对每个 panel 独立覆盖 loading、empty、request error、invalid ID、missing trace；

### R2-P2-02：统一 Ruff 命令、前端日志和 bundle gate 不可复现

**证据**

- BFF 的 ruff 只在 optional extra `dev`；观测后端虽有 `[tool.ruff]`，但 dev dependency 没有 ruff；
- 指南统一命令在初始环境均找不到 ruff，手工安装后源码才通过；
- 业务前端测试持续输出 React forwardRef warning、Ant Design deprecation、MSW 未匹配 GET；
- `QUALITY_FIX_RECORD.md` 称两个前端全绿，但观测前端真实 exit 1；
- 文档写“CI 待接入”，仓库没有实际 release gate；bundle 只记录预算，没有自动失败逻辑；
- 观测 build 当前含约 1.15 MB、1.47 MB chunk，与文档只记录约 250 kB 主入口不能等价证明整体预算。

**整改与验收**

- 三个 Python 项目统一使用 dependency group 或固定 tool runner，使指南原命令在干净 checkout 直接成功；
- CI 从 `uv sync --frozen` / `npm ci` 开始验证，不能依赖本地残留工具；
- 修复/隔离 React、MSW unhandled 输出；第三方确实不可修时必须以精确包版本、issue、过滤边界记录，不能吞所有 console error；
- 实现 bundle size 脚本，按入口和 lazy chunk 分别设置 gzip/raw 上限，超限 CI 失败或要求带编号批准；
- 修正质量记录，所有“全绿”必须附 exit code 和日志 artifact。

### R2-P2-03：Python 供应链未收口，DOMPurify 例外元数据不足

**证据**

- 锁文件审计发现 BFF 3 条 Starlette 已知漏洞记录；
- map_core 发现 30 条记录、11 个包，涉及 click、lxml、orjson、pydantic-settings、pygments、python-dotenv、python-multipart、setuptools、starlette、ujson、urllib3，审计均给出修复版本；
- 质量记录没有这些结果、owner、处置或例外；
- DOMPurify 记录的“升级卡号”只是描述性文字，没有可追踪编号；owner 也是角色而非可追责实体；
- 仓库没有实际依赖审计 CI gate。

**整改与验收**

- 在兼容约束下升级所有可直接修复包并跑 map_core 全量 125 项及 golden/ID 回归；
- 无法升级项逐条记录 advisory ID、可达性、缓解、owner、工单号、到期时间和批准人；
- 固化兼容 Python 版本的 `pip-audit` 命令/容器，标准命令 exit 0 或只命中已批准 allowlist；
- DOMPurify 例外补真实工单编号/owner，并验证项目实际没有进入受影响 API 模式；
- CI 对新 high/critical 和过期例外直接失败。

### R2-P2-04：OpenAPI 快照和校验脚本不能证明交付契约

**证据**

- `test_openapi_contract.py:74-86` 实际只把 OpenAPI 转为 `(method,path)` 集合；没有比较 request/response schema、required、type、status code 或 error envelope；
- 因此注释中的“无字段/type drift”未由测试实现；
- 两个 `scripts/verify_*.py` 按文档原命令均无法 import `app`；
- deploy test 在 import 前 `os.environ.setdefault(MAP_BFF_STATE_FILE, /tmp/...)`，因此 `create_app(settings=Settings())` 并非真正的无覆盖默认配置；
- readiness 只按 `code='default'` 查 seed，没有同时验证稳定 UUID 与配置值映射。

**整改与验收**

- 对规范化后的完整 OpenAPI schema 做 snapshot/diff，允许列表仅接受显式评审变更；
- runtime error test 参数化覆盖所有新 `/api/v1` operation 的 401/403/404/409/422/500；

- readiness 同时校验 `id=MAP_DEFAULT_WORKSPACE_ID AND code=default`，错误 UUID 必须 503。
