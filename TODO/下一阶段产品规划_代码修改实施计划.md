## 0. 如何使用本文

1. coding agent 不应以整份文档为一个任务。必须按 `F-* / R1-* / R2-* / R3-*` 工作包逐个实施；每个工作包单独分支、单独 PR、单独验收。
2. 工作包的“允许修改范围”是默认文件所有权边界。需要跨出边界时，必须先更新接口契约并在 PR 描述中解释原因，禁止顺手重构相邻模块。
3. 标记为 `阻塞依赖` 的工作包不得提前并行编码；标记为 `可并行` 的工作包只能在前置契约合并后并行。
4. 每个功能的验收同时包含：接口契约、数据正确性、权限、幂等、异常/回滚、自动化测试、文档。只完成 UI 或 happy path 不算完成。
5. 所有新增跨服务接口先更新 `SPEC/`，再写实现；旧接口除非本文明确要求，否则只做兼容扩展，不删除、不改事件名。
6. 本文中的目录和文件名是目标结构。若实施时有充分理由调整，必须保持职责边界不变，并同步修订本文。

### 1.3 对产品规划的校正

1. “会话后端持久化”必须提前到 R1 基础工程。否则消息级反馈没有稳定 `message_id`，评测坏例也无法追溯。R2 只开放搜索、收藏、分享等产品界面。
2. “身份上下文”必须提前到 R1，但 R1/R2 只实现开发模式和可信网关 Header 模式；真正 OIDC 登录在 R3。审计日志不能继续使用客户端自报 `operator`。
3. 评测运行本身是长任务，因此 R1 必须先有最小的持久化作业框架。R2 在同一框架上扩展用户长任务、通知和订阅，禁止另造第二套队列。
4. HITL 依赖 AgentScope 中断/恢复检查点。当前复审报告明确该能力尚未完成；`R2-HITL` 在 `F-AS-02` 通过前只能做 schema/API，不得声称可恢复执行。
5. R3 多租户为企业内部工作空间，不做公有云 SaaS 的租户计费、注册、域名和自助开通。

## 2. 总体技术决策（后续 agent 必须遵守）

### 2.1 数据所有权

| 数据类型 | 唯一事实源 | 说明 |
| --- | --- | --- |
| 用户、组织、工作空间、成员 | PostgreSQL / BFF | R1 先建立默认空间和 principal；R3 接 OIDC/组织同步 |
| 会话、消息、反馈、分享、订阅 | PostgreSQL / BFF | 属于产品数据，不写入 AdminState，不以 Mongo 观测记录代替 |
| 评测集、评测运行、评分、门禁报告 | PostgreSQL / BFF | 测试集可引用 Mongo 请求，但引用后要生成不可变快照 |
| 管理配置 | R1/R2：AdminState 文件为当前值，PostgreSQL 记录版本/审计；R3：PostgreSQL 为唯一事实源 | R1 双写必须有失败状态，不假装原子事务 |
| 异步任务、审批、通知、outbox | PostgreSQL / BFF worker | 使用租约、幂等键、重试和事务 outbox |
| 执行过程、request/agent/tool/LLM 事件 | MongoDB / map_core | R3 增加 PostgreSQL durable buffer 后再投影到 Mongo |
| Trace/Metric | OTel 后端 | Mongo 的 trace_id 只用于关联，不把 OTel 当产品状态库 |
| 预算配置 | PostgreSQL / BFF | 用量与成本明细从 map_core 运行事件投影，预算判断在 BFF/worker |

### 2.2 服务职责

```text
Browser / IM
    |
    v
map-business-backend (控制面 + 产品域 API)
    |- identity/workspace/RBAC
    |- conversation/feedback/evaluation/config audit
    |- task/approval/subscription/budget/compliance
    |- PostgreSQL repositories + transactional outbox
    |
    +--> map-worker（与 BFF 共用代码包、独立进程）
    |      |- durable job claim/heartbeat/retry
    |      |- evaluation/task/subscription/notification workers
    |
    +--> map_core（执行面）
            |- global/flow runtime
            |- evidence/refusal/checkpoint/tool approval boundary
            |- runtime events -> Mongo / R3 durable buffer

map-observability-backend
    |- 只读分析 Mongo/OTel 投影
    |- feedback bad-case/cost/SLA/AgentCase 审核视图所需聚合 API
    |- 不直接修改 BFF 产品表；写操作调用 BFF 内部 API
```

硬边界：

- 浏览器仍不得直连 map_core。
- map-observability 不得成为会话、评测集、预算或审批的事实源。
- BFF 不复制执行引擎；评测与订阅都通过冻结的运行时快照调用 map_core。
- map_core 不实现组织/RBAC 数据库；它只消费 BFF 注入且签名/可信的 runtime principal 和 scopes。
- R1/R2 不新增 Redis/Kafka。持久化作业采用 PostgreSQL `FOR UPDATE SKIP LOCKED` + lease；R3 若压测不满足再通过 adapter 切换消息队列，不在业务代码中绑定具体 broker。

### 2.3 兼容性规则

1. 现有 `/api/chat`、`/api/chat/stream/v2`、`/api/chat/flow/v1`、`/api/chat/stream/flow/v1` 保留到 R3 结束。
2. 新产品 API 统一使用 `/api/v1/...`；内部执行 API 使用 `/internal/v1/...`。
3. 现有 SSE 事件名 `start/meta/content_delta/done/error` 冻结。新信息通过 `meta.phase` 或 `done.meta` 增量加入，不能改变旧字段类型。
4. 所有写 API 支持或明确拒绝幂等：创建类使用 `Idempotency-Key`；更新类使用 `If-Match`/`version` 乐观锁；重复请求不得产生重复反馈、任务、审批或通知。
5. 所有时间写 UTC（带时区），API 返回 RFC 3339；前端再按 `Asia/Shanghai` 展示。cron 单独保存 IANA timezone。
6. 外部公开 ID 使用 UUID/ULID，不暴露数据库自增主键；日志中必须包含 `request_id/session_id/task_id/workspace_id`（适用时）。
7. API 错误统一为 `{code, message, details, request_id}`；产品逻辑不得以 HTTP 200 + `meta.fallback` 掩盖权限或数据校验失败。
8. `/internal/v1` 只接受服务身份（R1/R2 使用 secret reference 注入的短期/轮换 service token并校验 audience；R3 可升级 mTLS/workload identity），不接受浏览器用户 token；token 不得写日志。

### 2.4 默认产品决策

| 议题 | 本计划默认值 | 可变边界 |
| --- | --- | --- |
| 评测评分 | 规则断言 + LLM-as-Judge；人工抽检用于校准 | R1 不做模型微调和自动训练 |
| 评测执行 | 发布门禁默认 deterministic replay；可选 live tool run | live 结果不能单独作为阻断门禁，除非用例明确声明 |
| 工作空间 RBAC | 全局角色 + workspace resource scope | 不创建空间内独立角色定义系统 |
| IM | 先实现 connector SPI；钉钉/企微必须在 R1 结束前二选一 | R2 只交付一个渠道，不同时实现两套 |
| 成本治理 | R2 为软预算 + 80%/100% 告警 | R2 不因超预算强制拒绝请求；硬配额留后续 |
| 配置审批 | R1 审计所有写；高风险项支持可选双人审批的模型，R1 只对发布门禁强制 | 全量双人审批在 R3 生命周期流程统一完成 |
| OIDC | Authorization Code + PKCE，服务端 session cookie | R3 v1 不实现 LDAP 密码直连；可由企业网关转换为 trusted header |

#### F-AS-02：AgentScope 检查点/恢复能力

- 目的：给 R2 长任务恢复和 HITL 提供真实引擎能力。
- 阻塞依赖：F-AS-01；阻塞 R2-HITL，建议在 R1 期间完成。

- 检查点最少保存：引擎版本、agent/spec hash、messages、当前 iteration、pending tool call（名称、参数、call id）、已完成 tool results、runtime config version、request/session/task IDs。
- 检查点可能包含用户输入和工具参数：生产持久化必须使用带 `key_version` 的应用层加密或企业 KMS envelope encryption；日志、SSE、审计只出现 checkpoint ID/hash，不出现完整 state。
- 恢复必须校验：版本兼容、配置 hash、pending tool 是否仍存在、批准 grant 是否匹配；校验失败进入终态 `resume_incompatible`，不得静默从头执行副作用工具。
- 验收：在“LLM 后/工具前”和“工具后/下一轮 LLM 前”各强制中断一次，恢复后最终结果与不中断执行一致；副作用工具调用次数严格为 1；取消后不可恢复。

- 验收：业务前端 build 通过；核心交互测试通过；初始 JS chunk 比当前 1.46 MB 至少下降 30%，或在 PR 中给出不可达原因和后续拆包卡；视觉基线无明显变化。

#### F-03：PostgreSQL、Alembic、Repository 与最小作业框架

- 目的：提供 R1 产品数据和异步评测的可靠存储。
- 阻塞依赖：F-01；阻塞 R1-CONV、R1-FEEDBACK、R1-EVAL、R1-AUDIT。
- 允许修改：BFF `db/repositories/workers`、pyproject/lock、Compose、BFF tests、SPEC；不迁移 AdminState 当前值。
- 技术约束：SQLAlchemy 2.x async + asyncpg + Alembic；repository 不向 API 泄露 ORM model；事务由 service 层控制。
- 数据库边界：即使复用同一个 PostgreSQL 实例，也使用独立 `map_control` schema/数据库角色；BFF/worker 业务角色不能读 map_core 未来 event buffer 之外的执行表，map_core 不能读会话/反馈/身份表；Alembic 使用单独 migration role。
- 首批基础表：
  - `workspaces(id, code, name, status, created_at)`，种子 `default`；
  - `users(id, external_subject, staff_code, display_name, department_code, status, created_at, updated_at)`；
  - `jobs(id, workspace_id, job_type, status, payload_json, result_json, idempotency_key, priority, attempt, max_attempts, lease_owner, lease_expires_at, next_run_at, created_by, created_at, started_at, finished_at, error_code, error_message)`；
  - `outbox_events(id, aggregate_type, aggregate_id, event_type, payload_json, available_at, claimed_at, delivered_at, attempt, last_error)`；
  - `idempotency_records(workspace_id, principal_id, key, request_hash, response_status, response_body, expires_at)`。
- job 状态机：`queued -> running -> succeeded|failed|cancelled`；可重试失败为 `queued` 并增加 attempt；超时租约可被其他 worker 回收。
- worker：`python -m app.workers.main` 独立进程；Compose 单独服务；SIGTERM 停止领取新任务并等待当前 handler 的安全点。
- 验收：
  - 空库一次升级到 head、降级一版、再升级成功；
  - 两 worker 并发只领取一次同一 job；worker kill 后 lease 到期可回收；
  - 同一幂等键+同一 body 返回原响应，不同 body 返回 409；
  - outbox 与领域写入同事务提交；handler 重放不产生重复外部副作用。

#### F-04：统一身份、workspace context、请求/会话 ID

- 目的：让审计、反馈、会话、任务共用可信身份。
- 阻塞依赖：F-03；阻塞所有写功能。
- 允许修改：BFF core/dependencies/middleware、chat forwarding、前端 API client、map_core header 解析和契约测试。
- 模式：
  - `MAP_AUTH_MODE=dev`：仅非 prod；从配置创建固定本地管理员；
  - `trusted_header`：只信任受信代理来源，读取 subject/user/name/roles/department/workspace；
  - `oidc`：R3 启用。
- `RequestPrincipal`：`subject, user_id, staff_code, display_name, roles, department_code, workspace_id, auth_mode`。业务 service 只能依赖它，不得再读取任意 Header。
- 内部调用使用独立 `ServicePrincipal(service_name, audience, scopes)`，不能伪装成用户 principal；需要代表用户执行时同时传经签名/可信注入的 actor context，并由目标服务校验允许的 delegation scope。
- ID 所有权：浏览器/BFF 创建 `session_id`（一次会话稳定）；BFF 每次请求创建/接受合法 `request_id`；向 map_core 透传 `X-Request-ID/X-Session-ID/X-Workspace-ID`。map_core 仅在内部直调缺失时生成。
- 安全：生产环境遇到 `dev` 模式启动失败；trusted headers 未经可信代理时返回 401；管理写接口至少需要 `platform_admin` 或相应 workspace scope。
- 验收：BFF、core、Mongo request record、OTel trace 中四个 ID 一致；客户端传 `operator=other` 不影响审计 actor；跨 workspace ID 返回 404 或 403，不泄漏资源存在性。

## 4. 公共契约

### 4.1 标准证据模型

```json
{
  "evidence_id": "ev_...",
  "evidence_type": "kb_chunk|sql|tool_result|document|url|artifact|human_decision",
  "title": "订单 123 发货记录",
  "source_system": "enterprise_kb|text_to_sql|mcp_server_id|manual",
  "locator": "受权限保护的资源定位符或资源 ID",
  "excerpt": "脱敏后的短摘要",
  "query": "可选；脱敏后的检索词或 SQL",
  "tool_call_id": "tc_...",
  "agent_code": "Operations",
  "flow_node_id": "node_1",
  "confidence": 0.91,
  "visibility": "user|admin|audit_only",
  "metadata": {},
  "created_at": "2026-08-09T00:00:00Z"
}
```

约束：

- `evidence_id` 在一次请求内稳定且唯一；消息引用只存 ID，不复制未脱敏原文。
- `locator` 不能包含临时 token；需要访问外部内容时由 BFF 生成短期授权跳转。
- SQL 证据保存规范化 SQL、数据源 ID、返回行数、执行时间和结果摘要；默认不保存整表结果。
- KB 证据保存 chunk/document ID、版本和允许展示的 excerpt。
- 前端无证据时明确显示“本回答未产生可验证来源”，禁止构造 fallback 来源。

### 4.2 标准决策/拒答模型

```json
{
  "decision": "answer|clarify|refuse|handoff",
  "reason_code": "LOW_ROUTE_CONFIDENCE|INSUFFICIENT_EVIDENCE|TOOL_FAILURE_LIMIT|PERMISSION_DENIED|POLICY_BLOCKED",
  "message": "面向用户的稳定话术",
  "confidence": 0.58,
  "confidence_components": {
    "route": 0.61,
    "tool_success": 1.0,
    "evidence_coverage": 0.33,
    "judge": null
  },
  "suggested_questions": [],
  "retryable": true
}
```

约束：最终 confidence 是策略计算结果，不接受模型直接自报；缺失分量为 `null`，不得当 0；权限拒绝不得降级为普通工具失败。

### 4.3 SSE 增量

保留五类事件，新增以下 `meta.phase`：

- `decision_made`：携带标准决策模型；
- `evidence_collected`：单条或批量证据，允许边执行边到达；
- `evidence_bundle_finalized`：最终去重、排序、可见性过滤后的证据；
- `task_checkpointed`：仅异步任务，含 checkpoint ID，不含敏感状态；
- `approval_required` / `approval_resolved`：R2 HITL；
- `cost_updated`：可选增量，最终值以 done/meta 或账本为准。

`done.data` 增量字段：`message_id, conversation_id, decision, evidence[], config_snapshot_id, cost_summary`。旧客户端忽略这些字段仍能显示 content。

### 4.4 评测报告和发布门禁

发布门禁引用不可变对象：`asset_type + asset_id + candidate_version/hash + evaluation_run_id + report_hash`。以下任一情况门禁无效：配置 hash 不一致、数据集版本改变、run 未完成、关键 scorer 缺失、报告过期、workspace 不一致。

### 4.5 统一错误码和 HTTP 语义

| 场景 | HTTP | `code` |
| --- | --- | --- |
| 未登录/服务身份无效 | 401 | `AUTHENTICATION_REQUIRED` / `INVALID_SERVICE_IDENTITY` |
| 已登录但无 action/scope | 403 | `FORBIDDEN`；跨空间读取可按资源策略返回 404 |
| 资源不存在或不可见 | 404 | `RESOURCE_NOT_FOUND` |
| version/If-Match 冲突 | 409 | `VERSION_CONFLICT` |
| 幂等键复用但 request hash 不同 | 409 | `IDEMPOTENCY_CONFLICT` |
| 非法状态跳转/已结束任务再取消 | 409 | `INVALID_STATE_TRANSITION` |
| 评测/发布门禁失败 | 409 | `RELEASE_GATE_FAILED`，details 给出失败规则 |
| approval 过期/已消费/参数改变 | 409 | `APPROVAL_EXPIRED/CONSUMED/ARGUMENTS_CHANGED` |
| schema/业务输入非法 | 422 | `VALIDATION_ERROR`，details 为字段错误 |
| 速率限制 | 429 | `RATE_LIMITED`，带 Retry-After |
| 下游暂不可用 | 502/503/504 | `UPSTREAM_ERROR/SERVICE_UNAVAILABLE/UPSTREAM_TIMEOUT` |

同步 chat 的“算法不可用兜底文本”仅可作为兼容模式；新 `/api/v1` 接口要保留准确 HTTP/任务状态，不能把失败消息持久化为成功答案。

### 5.2 R1-CONV-01：会话与消息最小持久化

- 覆盖：为 E2 提供 message ID；为 R2 会话中心铺底。
- 前置：F-03、F-04。
- 允许修改：BFF conversations schema/repository/service/router；chat router 与前端 chat API/reducer；map_core 仅做 additive IDs。
- 明确不做：R1 不开放搜索、收藏、分享、批量管理；这些属于 R2。

数据表：

| 表 | 关键字段与约束 |
| --- | --- |
| `conversations` | `id, workspace_id, owner_user_id, mode(global|flow), title, status(active|archived|deleted), created_at, updated_at, last_message_at, version`；索引 `(workspace_id, owner_user_id, last_message_at desc)` |
| `messages` | `id, conversation_id, parent_message_id, role, status(pending|streaming|completed|failed|stopped|suspended), content, request_id, task_id, decision_json, config_snapshot_id, created_at, completed_at, version`；`request_id` 唯一（非空） |
| `message_evidence` | `message_id, evidence_id, ordinal, evidence_json, created_at`；联合主键，证据 JSON 已按 principal 可见性过滤 |

API：

- `POST /api/v1/conversations`：创建 global/flow 会话；幂等。
- `POST /api/v1/conversations/{id}/messages:stream`：BFF 先写 user/assistant pending message，再代理 core SSE；返回 SSE。
- `GET /api/v1/conversations/{id}`：R1 仅用于刷新恢复当前会话。
- `POST /api/v1/messages/{id}:stop`：停止仍连接的执行；异步 task 在 R2 扩展为 cancel。
- 旧 chat API 继续工作，但使用 ephemeral compatibility conversation，不进入 R2 列表，或通过 feature flag 自动持久化；这一选择要在 PR 契约中固定。

执行规则：

1. user message 与 assistant placeholder 在调用 core 前同事务落库。
2. content delta 不逐 token 写 PostgreSQL；BFF 在内存累计并按 250～500 ms/固定字符批量 checkpoint，done 时写最终 content。
3. 连接中断不等于任务失败：R1 同步流标记 `stopped`；R2 async 流由 worker 继续。
4. fallback 同步调用不能覆盖原始流错误事实；message 保存 `stream_error` 和 `fallback_used`。
5. `request_id/session_id/conversation_id/message_id` 写入 core runtime meta 和 Mongo request record（additive）。

验收：

- 浏览器刷新后能恢复当前会话的已完成消息和状态；跨用户/跨空间读取被拒绝。
- 同一 `request_id` 重试不创建第二条 assistant message。
- core 返回 error、BFF fallback、客户端 abort 三种路径状态分别准确。
- 流式过程中 BFF crash，重启后消息最多停留 `streaming`；reconciler 在超时后标记 `failed/interrupted`，不永久假运行。
- repository、API、SSE 集成测试覆盖；现有 chat API 契约测试继续通过。

### 5.3 R1-EVAL-01：评测数据集与用例管理

- 前置：F-03、F-04、F-AS-01。
- 允许修改：BFF evaluation domain/db/api；观测 backend 仅增加只读候选查询；业务前端评测页面在 R1-UI。

数据表：

| 表 | 关键字段 |
| --- | --- |
| `evaluation_datasets` | `id, workspace_id, name, description, scope_type(agent|scenario|global), scope_id, status, latest_version, owner_user_id` |
| `evaluation_dataset_versions` | `id, dataset_id, version, case_count, content_hash, created_by, created_at`；发布后不可变 |
| `evaluation_cases` | `id, dataset_version_id, external_key, query, history_json, runtime_context_json, expected_answer, expected_evidence_json, assertions_json, tags, severity, source_type(manual|feedback|request|golden), source_ref, enabled` |
| `evaluation_scorer_configs` | `id, workspace_id, name, scorer_type(rule|llm_judge), config_json, threshold, critical, version` |

用例断言 v1：

- `contains / not_contains / regex / json_path / numeric_tolerance`；
- `tool_called / tool_not_called / agent_selected / decision_equals`；
- `evidence_type_present / evidence_coverage_min`；

Scorer profile：`ci_replay` 只运行 deterministic rule scorers（另用 stub 测 judge 协议，不把 stub 分数当质量结论）；`release` 运行规则 + 真实 LLM judge + 可选人工抽检。发布策略明确绑定 profile，不能把 CI stub 报告用于生产发布。

### 5.4 R1-EVAL-02：评测运行器、评分与对比报告

- 覆盖：E1 一键回归、A/B 对比。
- 前置：R1-EVAL-01、F-03；可与 R1-EVIDENCE-01 部分并行，但最终 scorer 需等证据模型。
- 允许修改：BFF evaluation service/worker、map_core internal evaluation adapter、测试；禁止在评测代码复制 global/flow pipeline。

数据表：

| 表 | 关键字段 |
| --- | --- |
| `evaluation_runs` | `id, dataset_version_id, candidate_snapshot_id, baseline_snapshot_id, mode(replay|live), status, job_id, started_at, finished_at, totals_json, report_hash, created_by` |
| `evaluation_case_runs` | `id, run_id, case_id, side(candidate|baseline), request_id, status, answer, decision_json, evidence_json, latency_ms, token_usage_json, cost_json, error` |
| `evaluation_scores` | `case_run_id, scorer_config_id, score, passed, reason, raw_output_json`；联合唯一 |
| `evaluation_comparisons` | `run_id, case_id, metric, candidate_value, baseline_value, delta, regression` |

执行模式：

1. `replay`：工具调用由 golden adapter 按 tool name + normalized args 回放；禁止写库/发消息类真实工具。用于 CI 和强制发布门禁。
2. `live`：使用真实只读工具；副作用工具无条件 denied；结果标记数据时点。用于人工观察，不默认阻断。
3. candidate/baseline 都引用不可变 config snapshot；评测开始后管理端继续编辑不影响本次 run。
4. LLM judge 固定 judge 模型、prompt version、temperature=0，并保存原始结构化输出；judge 失败不允许默认为通过。

内部接口：

- `POST /internal/v1/evaluations/execute`，接受单 case + runtime snapshot + replay bundle，返回统一 answer/decision/evidence/usage；仅 BFF worker 可访问。
- 如继续复用现有 chat endpoint，必须通过 `execution_mode=evaluation` 在 ToolAdapter/Executor 层强制副作用隔离，不能只靠 prompt 提醒。

报告：总通过率、critical case 通过率、各 scorer 均分、相对 baseline 回归数、P50/P95 latency、token/cost delta、失败 case drill-down、报告 hash。

验收：

- 12 条 seed dataset 在无外网/无模型密钥环境下使用 `ci_replay` profile 完成；judge adapter 的 schema/error 由 deterministic fake 单独测试。
- 两个 worker 并发运行，同一 case/side 仅执行一次；失败重试不重复副作用。
- candidate 故意删除必需工具时，`tool_called/evidence` scorer 稳定失败；judge unavailable 时 run 状态为 partial/failed，门禁不通过。
- 取消 run 后不领取新 case，进行中 case 到安全点停止；报告明确 cancelled 数。
- 对比报告相同输入运行两次的 rule scorer 结果一致；LLM judge 波动通过校准集监控。

### 5.5 R1-FEEDBACK-01：消息级反馈与纠错

- 覆盖：E2。
- 前置：R1-CONV-01；与 R1-EVAL-02 可并行。
- 允许修改：BFF feedback domain/api/db、业务前端 message actions；观测投影在 R1-OBS。
- 反馈枚举：`helpful/unhelpful`；点踩原因至少 `incorrect/outdated/no_evidence/not_relevant/unsafe/too_verbose/tool_failed/other`；可选 correction 文本。

表 `message_feedback`：`id, workspace_id, conversation_id, message_id, request_id, user_id, rating, reason_codes, correction_text, status(open|converted|dismissed), created_at, updated_at, version`；联合唯一 `(message_id,user_id)`。

API：

- `PUT /api/v1/messages/{message_id}/feedback`：创建或覆盖当前用户反馈；幂等。
- `DELETE .../feedback`：撤回，审计保留事件但产品当前值删除/标记 withdrawn。
- `GET /api/v1/admin/feedback`：按空间、Agent、场景、原因、日期筛选。
- `POST /api/v1/admin/feedback/{id}:convert-to-evaluation-case`：必须选择 dataset draft/version 和确认脱敏预览；重复转换返回已有 case。

隐私/安全：纠错文本走统一脱敏；普通用户只能操作自己的反馈；管理员看坏例需 audit scope；反馈不能修改原消息内容。

验收：

- 点赞、改点踩、补原因、撤回四条路径刷新后状态一致。
- 同一用户重复点击不重复计数；两用户独立计数。
- 点踩转换用例保留 source_ref、message/request/config snapshot/evidence，且去掉 token、authorization、audit_only 证据。
- 北极星“答案采纳率”口径有可执行查询：`helpful / (helpful + unhelpful)`，无反馈不得自动当 helpful；“未追问纠错”另作推断指标，不和显式反馈混算。

### 5.6 R1-EVIDENCE-01：执行侧标准证据采集

- 覆盖：E3 后端。
- 前置：F-AS-01；证据 schema 先合并后可与 BFF 工作并行。
- 允许修改：map_core schema、ToolResult/AgentResult additive 字段、工具 adapter、global/flow summary、SSE；`packages/map-tree-core` 仅扩类型和定位 API。
- 实施：
  1. 新建 `schema/evidence_schema.py` 与 `service/evidence_collector.py`，请求隔离实例，按 fingerprint 去重。
  2. 在 KB、uploaded file、ask database、wenshu、web search、MCP、prompt skill adapter 建 evidence converter；不认识的工具只生成 `tool_result` 摘要，不能伪装成原始数据证据。
  3. `NodeExecutionResult.evidence_refs` 改为真实 evidence IDs；`matched_evidence` 对 evidence contract 做显式匹配。
  4. summary prompt 接收编号证据清单；最终 meta 返回 answer citation IDs。无效 citation 在 finalizer 移除并记录 validation issue。
  5. Mongo request/end 或独立 `evidence_records` 记录审计所需证据；大 payload 只存 hash/locator/摘要。

工具验收矩阵：

| 工具类型 | 必须提取 | 禁止 |
| --- | --- | --- |
| KB | kb/document/chunk ID、文档标题、版本、短 excerpt | 整篇文档、鉴权 token |
| SQL/问表 | datasource/model ID、规范化 SQL/查询 JSON、row count、摘要 | 默认保存完整敏感结果集 |
| 问数 | metric/dimension codes、数据时点、查询摘要 | 把 LLM 总结当原始指标证据 |
| Web | URL、标题、抓取时间、短摘要 | 无 URL 的“网络来源” |
| MCP | server/tool/call ID、安全摘要、原始结果 hash | server headers/env refs |
| 人工决策 | approval ID、decision、actor 展示名、时间 | 审批人的凭证/完整组织 claims |

验收：

- 每类工具至少一个 contract test；证据 ID 在 SSE、done、Mongo、会话消息中一致。
- flow evidence contract 覆盖率可计算：matched/required；缺失项进入 `missing_evidence`。
- 来源卡能跳到对应调用树 tool_call_id/flow_node_id；目标不存在时显示失效，不跳错节点。
- 敏感字段 fuzz 测试证明 `api_key/token/authorization/password/secret/cookie` 不进入 evidence。
- R1 指标定义：“应溯源回答”=使用外部工具或 scenario 声明 evidence contract 的成功回答；其中 evidence bundle 非空且引用校验通过的比例 ≥80%。纯闲聊不进分母。

### 5.7 R1-DECISION-01：置信度、澄清与拒答策略

- 覆盖：E4。
- 前置：R1-EVIDENCE-01；可与 UI 并行。
- 允许修改：BFF AdminState schema/config API，map_core scene selector/global/flow policy evaluator，前端 decision UI。

管理配置新增 `decision_policy`：

- `route_confidence_threshold`、`route_margin_threshold`；
- `minimum_evidence_coverage`；
- `max_consecutive_tool_failures`；
- `on_low_route_confidence=clarify|fallback|refuse`；
- `on_insufficient_evidence=clarify|refuse|answer_with_warning`；
- 各 reason_code 的用户话术与建议问题模板；
- enabled/scenario/agent overrides（R1 只支持全局 + Agent，workspace override 到 R3）。

执行切面：

1. 场景选择后先判 route threshold，低于阈值不得继续硬路由高风险 Agent。
2. ToolExecutor/AgentRuntime 统计连续失败；权限 denied 单独处理，不计为普通 retry。
3. 心流节点依据 verdict/evidence coverage 决定 repair、人工（R2）或拒答。
4. final decision 在 summary 前冻结；若为 refuse，summary 不能覆盖成普通答案。

验收：

- 阈值边界（小于、等于、大于）、双场景 margin、不含 confidence、工具连续失败、证据不足、权限拒绝都有 deterministic 测试。
- 用户界面区分“需要补充信息”“暂时无法回答”“无权限”“系统失败”，不统一显示未知错误。
- 每个非 answer 决策包含稳定 reason_code、可读原因和下一步建议；观测可按 reason_code 聚合。
- 调低/调高策略热更新只影响新请求；每个请求记录生效 policy version/hash。

### 5.8 R1-AUDIT-01：配置写入统一化与不可抵赖审计

- 覆盖：G1 的审计部分。
- 前置：F-03、F-04、F-01。
- 允许修改：BFF config service/repository/audit db/api，所有 `/api/admin/*` 写路由；管理前端审计页在 R1-UI。

表 `config_audit_events`：

- `id, workspace_id(nullable for global), resource_type, resource_id, action, actor_user_id, actor_subject, actor_roles, request_id, source_ip, user_agent, before_version, after_version, json_patch, before_hash, after_hash, status(applied|failed|rejected), failure_code, prev_entry_hash, entry_hash, created_at`。

另设可变的编排表 `config_mutations(id, resource, expected_hash, target_hash, status(pending|applied|failed), error, created_at, finished_at)`；它用于崩溃恢复，不代替 append-only audit event。

实现规则：

1. 所有 AdminState 写必须经过 `ConfigMutationService`；禁止 router 内 `store.update(lambda ...)`。
2. diff 使用标准 JSON Patch 或等价稳定格式；list 项用稳定业务 key 对齐，不能因为排序变化输出整表删除/新增。
3. secrets 先 redaction 再写 diff；headers/env_refs 只存键名与变更标记。
4. R1 双写顺序：先创建 pending mutation，再带 expected AdminState hash 原子写文件，再追加一条 applied/failed audit event并结束 mutation。进程若在文件写后、审计追加前崩溃，启动 reconciler 根据 mutation 的 before/target hash 定位结果，并追加带 `recovered=true` 元数据的 applied 或 failed 事件。审计事件不能因产品写失败而消失。
5. `entry_hash` 串联前一条 hash；提供校验命令/API；数据库应用角色对审计表只有 insert/select、无 update/delete 权限（迁移角色除外）；mutation 表可由 service 更新。
6. AdminState 解析失败不得再静默回默认并覆盖原文件；启动/读取返回明确错误，保留坏文件供恢复。

API/UI：`GET /api/v1/admin/audit-events` 支持时间、actor、resource、action、status、request_id 搜索；详情显示脱敏 diff 与 hash 校验状态；只读审计员角色可访问但不能改配置。

验收：

- 对每个现有 Admin PUT/POST 做参数化测试，均产生准确 actor/diff/hash/status。
- 伪造 operator 不改变 actor；并发基于旧 hash 更新返回 409，不覆盖新值。
- 模拟 state file 无权限/磁盘写失败，API 失败且有 failed audit；原文件不被半写（临时文件 + fsync + atomic rename）。
- 手工篡改审计行后 hash chain 校验失败并定位第一条断点。

### 5.9 R1-GATE-01：Prompt/模型发布门禁

- 覆盖：E5；扩展现有 Master publish/rollback。
- 前置：R1-EVAL-02、R1-AUDIT-01。
- 允许修改：BFF asset snapshot/release gate service，Master 与 Business Agent publish API；前端发布对话框。

数据：`config_snapshots(id, resource_type, resource_id, version, content_json, content_hash, created_by, created_at)`；`release_gates(id, snapshot_id, evaluation_run_id, policy_json, report_hash, status, expires_at)`；现有 `release_history` 暂时兼容投影。

门禁默认规则：

- critical cases 100% 通过；
- 总通过率不得低于 workspace/asset 阈值；
- 相比 baseline 的 critical regression = 0；
- groundedness/evidence scorer 达阈值；
- run 的 candidate content_hash 必须等于待发布内容；
- report 未超过配置有效期（建议 7 天）。

R1 强制门禁范围：Master/Business Agent 的 prompt、route/summary model、temperature/max tokens、tool/skill 挂载和默认运行模型指针。模型 provider URL/secret 轮换走连通性测试+审计，不把 secret 放入评测 snapshot；纯展示名/描述修改不触发效果评测。权限、decision policy 等安全配置走各自策略测试/审批，不能用效果评测替代安全审查。

发布行为：

1. 保存草稿只产生 config snapshot，不影响 current。
2. 发起评测绑定 snapshot；评测通过后才可 publish。
3. Master 与 Business Agent 使用同一 state machine/API 语义；不能只有 Master 有门禁。
4. emergency bypass 默认关闭；启用时要求 `platform_admin + break_glass`、理由、到期时间，并产生高风险审计/告警。
5. rollback 到已发布版本不强制重跑评测，但必须记录 rollback reason；若目标版本已被安全下线则拒绝。

验收：

- 无 run、run 失败、hash 不匹配、报告过期、跨空间 run、critical regression 均阻止发布。
- 评测通过后修改一个空格导致 hash 改变，旧门禁失效。
- 发布与 current pointer/audit/release record 要么全部成功，要么 current 不变并记录 failed。
- API 并发发布同一版本只有一个成功；Business Agent 从“测试配置字段”升级为真实 draft/evaluated/published 状态。

### 5.12 R1 版本总验收

7. 运维：新增表有 migration、索引、备份说明；worker 有 health/readiness；README/SPEC/OpenAPI 更新。

- `GET /api/v1/tasks`、`GET /api/v1/tasks/{id}`、`POST ...:cancel`、`POST ...:retry`（仅 retryable 终态）。
- `GET /api/v1/tasks/{id}/events?after_seq=N`：SSE 带 `id: <seq>`，支持 `Last-Event-ID`；先重放 DB 事件再等待新事件。
- 在线等待使用 PostgreSQL `LISTEN/NOTIFY` 作为唤醒提示并保留短轮询兜底；NOTIFY payload 不承载事实数据，丢通知后仍能从 `task_events` 按 seq 补齐。
- worker 消费 map_core SSE 时必须“先持久化 task_event，再向在线客户端广播”；客户端 ack 不影响任务执行。
- 进度：心流用完成节点数/总节点数；全域未知总量时用阶段枚举而非伪百分比。

可靠性：

1. worker heartbeat/lease；失联后任务回收。若无安全 checkpoint，只能以新 attempt 从头执行只读链路；含已执行副作用时不得自动重跑。
2. cancel 是状态机命令：queued 立即取消，running 发送 cooperative cancellation，awaiting_approval 撤销 approval；完成后的 cancel 返回 409。
3. task event seq 单调；重放可重复但前端按 seq 去重。
4. message 最终内容与 task succeeded 在同事务提交；失败保留部分内容并明确 incomplete。
5. task 结束不依赖浏览器 SSE 连接；刷新/换设备可继续看同一用户任务。

验收：

- 发起后立即关闭页面，任务继续并最终写会话；重新打开从上次 seq 恢复。
- 模拟网络断开/重复连接/Last-Event-ID 过旧，事件无顺序倒退、无内容重复。
- kill worker 后 lease 回收；只读任务最终完成，副作用任务停在需人工处理状态。
- 同一幂等键重复创建只有一个 task；retry 产生新 attempt 但沿用 logical task ID/关联原 attempt。
- 以注入故障测试统计，“不因客户端断连丢失”的长任务完成率 ≥99%；分母排除用户主动取消和明确业务失败。

### 6.5 R2-HITL-01：工具执行前确认与人工裁决

- 覆盖：U3。
- 硬前置：F-AS-02、R2-TASK-01、F-04。F-AS-02 未验收不得合并真实执行路径。
- 允许修改：Admin 工具策略、map_core ToolAdapter/Executor/flow checkpoints、BFF approvals domain/worker/api；普通工具业务实现只允许适配审批 metadata。

管理模型：每个 tool/skill 配 `risk_level(low|medium|high|critical)`、`approval_mode(none|requester|designated_role|specific_users)`、`approver_roles/users`、`timeout_s`、`on_timeout(deny|cancel)`、`argument_preview_fields`、`always_require_for_actions`。服务端根据 tool identity 决定，客户端不能把 `requires_approval=false` 覆盖策略。

表 `approval_requests`：

- `id, workspace_id, task_id, checkpoint_id, tool_name, tool_call_id, risk_level, requester_id, approver_policy_json, sanitized_args_json, args_hash, status(pending|approved|rejected|expired|cancelled|consumed), decision_by, decision_reason, expires_at, decided_at, consumed_at, version`。

API：`GET /api/v1/approvals?status=pending&cursor=`、`GET /api/v1/approvals/{id}`、`POST /api/v1/approvals/{id}:approve`、`:reject`；决定请求必须带 `Idempotency-Key` 和当前 version，服务端重新检查 approver 权限。

执行时序：

1. ToolAdapter 在真实工具调用前评估策略。
2. 需要确认时保存 checkpoint 和原始参数 hash，发 `approval_required`，task 转 `awaiting_approval`；不能先调用工具再补审批。
3. BFF 创建 approval + 通知审批人；审批人看脱敏参数和风险说明。
4. approve 生成与 `approval_id + tool_call_id + args_hash + checkpoint_id` 绑定的一次性 grant；worker 恢复 task。
5. ToolAdapter 再校验 runtime permission 和 grant，执行一次，原子标记 consumed；修改参数必须重新审批。
6. reject/expire/cancel 注入结构化结果，策略决定拒答或走无副作用替代路径；不得自动改成 approved。

人在环路节点：心流 `uncertain` 可在节点边界创建 `human_decision` approval，裁决 `accept/retry/choose_candidate/abort`；R2 v1 不提供自由编辑执行图。

安全/竞态：申请人与审批人分离策略可配；critical 默认禁止 self-approve；双击 approve 只有一次生效；审批后 task 取消则 grant 失效；过期 grant 不能执行；所有决策进 audit。

验收：

- 针对写库/发送类 fake tool 证明未批准调用计数=0、批准后=1、重复恢复仍=1。
- args hash 不一致、跨 task grant、过期/已消费 grant、无 approver role 均拒绝。
- worker/core 任一点 crash 后恢复不绕审批、不重复副作用。
- requester 与审批人的前端分别看到正确状态；审批卡不展示密钥/完整敏感 payload。
- uncertain flow 人工选择 candidate 后从正确节点继续，已通过节点不重复执行。

### 6.11 R2 版本总验收

1. 会话：历史可搜索/重命名/收藏/分享；权限和 token 安全测试通过。
2. 长任务：客户端断连不影响执行，注入故障完成率 ≥99%；事件可从 seq 重放。

6. 成本：用量账本幂等，价格版本正确，80%/100% 告警去重；看板权限正确。
7. 产品目标：试点口径下 WAU 环比 +50%、IM 提问占比 ≥30%；若未达成，技术版本仍可完成，但产品验收标记“功能通过/指标待观察”，不能伪造。
8. 回归：R1 发布门禁、证据、反馈、审计全部保持；现有 API compatibility suite 全绿。

目标表：

- `config_resources(id, workspace_id nullable, resource_type, resource_key, current_version_id, status, version)`；
- `config_versions(id, resource_id, version_label, schema_version, content_jsonb, content_hash, lifecycle_state, created_by, created_at)`，发布后不可变；
- `config_deployments(id, resource_id, version_id, environment, rollout_policy_json, status, deployed_at, retired_at)`；
- 对高查询/关联资产（Agent/Skill/Scenario）使用规范化资产表；其余小型 section 可版本化 JSONB，但必须有 Pydantic schema_version。

迁移阶段：

1. `inventory`：读取现有 JSON，严格 validate，输出 section count/hash/unknown fields；不写 DB。
2. `import`：幂等导入 default workspace，保存原文件 hash 和 import batch；重复执行不重复。
3. `shadow-read`：仍从文件服务，后台同时读 DB 比较 hash/响应；差异告警。
4. `dual-write`：可选短窗口；以 DB transaction 为准，文件只作兼容导出；任何差异阻止切换。
5. `cutover`：维护窗口冻结管理写，最终同步，切 repository flag 到 postgres，运行 smoke/eval。
6. `rollback window`：保留 file export adapter 一版本；回滚需确认期间 DB 新变更已导出，不能简单切旧文件。
7. 稳定后删除运行时文件写入；文件保留为样例/备份导出，不挂载共享 RW volume。

并发/缓存：乐观锁 version；snapshot 以 content hash ETag；map_core provider支持 `If-None-Match`、stale-while-revalidate 和明确 stale 标志；配置变更通过 outbox invalidation，不依赖单进程内存。

验收：

- 当前真实 AdminState 导入后每个 section 语义等价、hash 可解释；shadow 运行 24 小时零未解释 diff。
- 两 BFF 副本并发更新无 lost update；map_core 在缓存过期/DB短暂失败时按策略使用最后已知好版本并标 stale。
- cutover/rollback 演练有时间、步骤和数据一致性记录；迁移脚本可重入。
- R3 后 `MAP_BFF_STATE_FILE` 不再是生产必需配置，BFF 可无共享文件水平扩展。

### 7.5 R3-ASSET-01：统一资产生命周期与灰度

- 覆盖：G3，承接 R1 发布门禁。
- 前置：R3-CFG-01、R3-WS-01、R1-GATE-01。
- 允许修改：BFF asset domain/state machine、Agent/Skill/Scenario APIs、runtime snapshot rollout resolver、管理前端；map_core 只接受解析后的版本。

统一状态机：

```text
draft -> testing -> evaluated -> canary -> published -> retired
  |        |           |          |          |
  +------ rejected <---+----------+----------+
```

- draft 可编辑；其他状态引用 immutable version。
- testing 必须绑定测试计划；evaluated 必须有有效评测报告；canary 必须配置人群/比例/时间和自动停止阈值；published 作为默认；retired 新请求不可选、历史可回看。
- `asset_versions` 统一元数据：type(agent|skill|scenario_pack|repair_policy)、workspace、semantic version、content hash、dependencies、created_by。
- `rollout_rules`：stable hash(`workspace_id,user_id,asset_id`) 分桶，确保同一用户稳定；允许 allowlist/department；规则冲突有确定优先级。
- runtime 每个 request 记录实际 asset version map；回滚只改 deployment pointer，不删版本。

安全：Skill/Scenario 依赖不存在/retired、权限 scope 扩大、增加 high-risk tool 时自动把风险升为 high 并要求审批；canary 不可绕过 workspace/role 权限。

API：统一 `/api/v1/assets/{asset_type}/{asset_id}/versions`；状态命令 `:submit-test/:mark-evaluated/:start-canary/:publish/:retire/:rollback`，每个命令接受 expected version、关联 eval/approval ID 和 idempotency key；旧 Master/Agent publish 路由做兼容 adapter。

验收：非法状态跳转全部拒绝；无评测不能 evaluated/canary/publish；10,000 个固定 user ID 的灰度比例误差在允许范围且重复运行分桶稳定；达到错误率/反馈阈值自动停止 canary 并通知；回滚后新请求使用旧版本、运行中请求不变。

### 7.6 R3-CASE-01：AgentCase 经验审核与场景演化

- 覆盖：G5、心流 Phase 4。
- 前置：R3-ASSET-01、R1 反馈/评测/证据。
- 允许修改：map_core AgentCase schema/miner 输出；BFF AgentCase candidate/review service；业务管理前端审核页面；观测端只增加 trace deep link；不得让 miner 自动发布生产策略。

表：

- `agent_cases(id, workspace_id, source_request_id, scenario_ids, query_fingerprint, graph_trace_ref, evidence_summary, outcome_metrics, quality_score, status(candidate|reviewing|accepted|rejected|expired), created_at)`；
- `policy_candidates(id, agent_case_id, asset_type(hyperedge|repair_policy|scenario_example), proposed_content, rationale, risk_level, status, reviewed_by, reviewed_at)`。

候选准入：成功请求、无安全/权限错误、evidence coverage 达阈值、显式 helpful 或人工选中、脱敏通过；相似 query/graph fingerprint 去重；低质量 trace 不进入审核队列。

流程：candidate → 人工比较原 trace/证据/建议 diff → accepted 后创建 asset draft → 走评测 → canary → publish。任何阶段都不能直接修改 active ScenarioHub。

API：`GET /api/v1/agent-cases`、`GET /api/v1/agent-cases/{id}`、`POST ...:accept/:reject`、`POST /api/v1/policy-candidates/{id}:create-asset-draft`；accept 和 create draft 分开，避免一次点击越过审核确认。

验收：点踩/低证据/被合规删除 request 不生成或自动失效；重复 trace 聚合频次但不重复候选；accept 只创建 draft；全链路保留 source/audit；canary 回退不删除 AgentCase。

### 7.7 R3-HA-01：运行事件可靠性与服务水平扩展

- 覆盖：D2 事件可靠性和多副本。
- 前置：R3-CFG-01；与 Helm 可并行。
- 允许修改：map_core state_store 新 adapter、PostgreSQL event buffer/relay、观测幂等写、压测；不改变 Mongo 对外分析 schema（只增 event_id 等）。

设计：用 PostgreSQL durable event buffer 替换“有界内存队列为唯一入口”。

- 在独立 `map_runtime` schema 中建立 `runtime_event_outbox(event_id, workspace_id, request_id, state_id, seq, event_type, payload_json, trace_id, span_id, occurred_at, status, attempt, next_retry_at, delivered_at)`；唯一 `(state_id,seq)` 与 `event_id`；map_core/relay role 不获得 `map_control` 产品表权限。
- map_core 在关键事件（request start/end、tool call/result、LLM usage、approval checkpoint）同步/批量可靠写 buffer；非关键高频 thought 可按策略采样。
- relay 多副本 claim，Mongo 使用 event_id upsert；成功后标 delivered；失败指数退避/dead letter。
- 背压：DB 不可用时关键事件按 fail policy（生产默认拒绝新高风险/异步任务，普通聊天允许有限本地磁盘 WAL 或明确 degraded）；不得无声丢弃。

多副本：BFF 无文件状态；worker lease；map_core 请求隔离；sticky session 不作为正确性前提；stream 断开后的任务由 BFF task events 恢复。

验收：

- 在 buffer→Mongo 各点 kill 进程，最终 Mongo 每事件恰一条（允许传输 at-least-once，投影幂等）。
- 队列积压、DB故障、Mongo故障有 metric/alert；恢复后按 seq 投影。
- 并发压测目标需在实施前记录硬件基线；至少验证 2 BFF + 2 core + 2 worker，无配置不一致/重复工具副作用/事件丢失。
- 禁止继续在 `fire_and_forget` 队列满时只打印日志；旧 dispatcher 在 feature flag 下保留一个版本回滚。

### 7.8 R3-DEPLOY-01：Helm/Kubernetes 企业交付物

- 覆盖：D2。
- 前置：R3-CFG-01 的无共享文件运行；R3-HA 可并行开发。
- 允许修改：`deploy/helm/map/`、Dockerfiles、settings/health、SPEC/运维文档；不得把真实 secret 写 values。

Chart 最少包含：frontend、BFF、worker、map_core、observability frontend/backend、OTel Collector；Postgres/Mongo 默认作为 external dependency，dev values 可选依赖 chart，但生产 values 不自动部署单实例数据库。

K8s 要求：

- startup/readiness/liveness 分离；readiness 检查关键依赖但避免级联雪崩；
- Deployment 滚动升级、PDB、anti-affinity/topology spread、HPA（CPU + 自定义 queue/latency 指标）；

- Secret/ExternalSecret 引用、ConfigMap、ServiceAccount 最小权限、NetworkPolicy、non-root/read-only rootfs/seccomp、资源 requests/limits；
- Ingress SSE timeout/buffering 配置；IM webhook 独立 path/限流；
- image tag 必填且不可使用 `latest`；所有 Pod 暴露 build SHA/version。

验收：`helm lint/template` 多 values 通过；kind/k3d smoke 安装、升级、回滚；滚动升级中短请求无明显错误、异步任务不丢；删除任一 Pod 后服务恢复；错误 migration 不更新应用；安全 context policy 检查通过。

### 7.9 R3-CICD-01：CI/CD 与评测门禁

- 覆盖：D3。
- 前置：R1-EVAL、R3-DEPLOY；基础 CI 可在 R1 提前建立。
- 允许修改：`.github/workflows/`（或企业 CI 等价目录）、scripts、Docker/Helm versioning、文档。

流水线：

1. PR：Python lint/type（逐步启用）、三个后端测试、两个前端 test/build、OpenAPI/contract diff、migration upgrade/downgrade、`ci_replay` golden eval、Helm lint、secret scan、依赖/镜像漏洞扫描。
2. main：构建多架构镜像，tag=`semver + git sha`，生成 SBOM，签名，推 registry；不得只构建未测试工作区。
3. preprod：部署指定 SHA → migration → smoke → live canary eval → 性能基线 → 人工批准。
4. prod：GitOps/受控部署；先 canary BFF/core/worker，再全量；自动检查 error/latency/eval guard；失败自动停止并支持回滚。
5. 版本清单：代码 SHA、镜像 digest、Helm chart、DB migration head、config snapshot versions、evaluation report hash 可一处查询。

门禁分层：PR 只用 deterministic replay，不依赖外部密钥；preprod live eval 可使用受控只读凭据；prod 不在部署时临时调用不稳定 judge 决定唯一成败，而使用已签名报告 + runtime health guard。

验收：故意破坏 contract/migration/golden case/image scan 阈值均能阻断；同一 artifact 从 preprod promote 到 prod，不重新 build；部署页面能回答“环境运行什么代码/配置/迁移/评测报告”；回滚演练包含应用和兼容 migration 策略。

### 7.13 R3-COMP-02：保留策略、删除权与删除证明

- 覆盖：D4。
- 前置：R3-COMP-01、R3-WS。
- 允许修改：BFF compliance domain/worker、Mongo TTL/index/删除 adapter、管理 UI、审计；外部工具数据只做已声明 connector。

表：

- `retention_policies(id, workspace_id, data_class/conversation/events/audit, retention_days, legal_basis, version, effective_at)`；audit 最低保留由安全策略限制，不能被普通 workspace admin 降到不合规值。
- `deletion_requests(id, workspace_id, subject_user_id, scope, status, requested_by, approved_by, started_at, completed_at, failure_summary, receipt_hash)`；
- `deletion_steps(request_id, system, status, counts_json, cursor, error, completed_at)`。

删除流程：冻结/校验 scope → PostgreSQL 产品数据匿名化或删除 → Mongo request/agent/tool/LLM/evidence/feedback projection 删除 → OTel 后端按可用 API/TTL → 搜索/缓存/分享 token → 生成不含已删内容的 receipt。不可承诺无法控制的第三方已删除，receipt 标 partial。

API：`GET/PUT /api/v1/admin/retention-policies/{data_class}`、`POST /api/v1/compliance/deletion-requests`、`GET /api/v1/compliance/deletion-requests/{id}`、管理员 `:approve/:reject`、安全审计员下载不含原文的 receipt；普通用户只能请求/查看自己的删除任务。

TTL：Mongo 文档增加 `expire_at` 并建 TTL index；更新策略只影响新数据还是回算历史数据必须可配置并审计；PostgreSQL 由 worker 分批 cursor 删除，避免长事务。

验收：用户/空间/时间范围三类删除；中途失败可从 step/cursor 恢复；幂等重跑；删除后产品/API/search/share/observability/export 均不可返回原文；聚合指标保留时必须不可重新识别；receipt hash 可验证；审计仅保留必要元数据。

### 7.14 R3 版本总验收

1. 多空间：至少 3 个部门独立运营；配置/数据/观测/成本/分享全链路隔离测试通过。
2. 生命周期：Agent/Skill/Scenario Pack 都走 draft→test/eval→canary→publish→retire；无有效评测不能发布；灰度可自动停止/回滚。
3. 身份：OIDC 生产链路、组织映射、停用回收、break-glass 审计通过内部安全评审。
4. 高可用：无 AdminState 共享文件；多副本故障注入无 lost update、无重复副作用；可靠事件最终投影且可观测。
5. 交付：Helm 安装/升级/回滚；CI 从源码到签名镜像和部署全链路；环境版本清单完整。
6. 告警/SLA：关键故障能告警、去重、恢复；月度 SLA 可重算且区分业务拒答/系统错误。
7. 合规：空间级 TTL、用户删除、统一脱敏、删除证明通过测试；完成一次内部安全评审。
8. AgentCase：高质量 trace 只生成候选，人工审核后才成为 draft，并经过评测/灰度；不存在自动直发生产路径。

## 10. 自动化测试与验收体系

### 10.1 测试分层

| 层 | 必须覆盖 | 运行位置 |
| --- | --- | --- |
| Domain unit | 状态机、策略阈值、hash、cron、预算 decimal、权限决策 | 每次 PR |
| Repository | workspace predicate、事务、乐观锁、幂等、lease、outbox | 每次 PR，真实 Postgres container |
| API contract | OpenAPI snapshot、错误 envelope、权限、pagination、If-Match/Idempotency-Key | 每次 PR |
| SSE contract | 分帧、event order、meta additive、Last-Event-ID replay、断流 | 每次 PR |
| Core golden | global/flow、legacy/agentscope、evidence/decision/tool governance | 每次 PR replay |
| Cross-service integration | browser→BFF→core→DB/Mongo；trace/IDs 一致 | main/preprod |
| Frontend component | loading/empty/error/403/409/stream/reconnect/a11y | 每次 PR |
| E2E | feedback→case→eval→publish；task→approval→resume；subscription→notify；workspace isolation | main/preprod |

| Performance | sync P95、task throughput/backlog、search、eval concurrency、event relay | 每版本候选 |
| Security/compliance | auth/token、cross-space、secret/PII fuzz、delete proof、dependency/image scan | PR + release |

### 10.2 必须新增的测试目录/工具

- `map-business-backend/tests/contracts/`：OpenAPI 和跨版本响应 fixture。
- `map-business-backend/tests/integration/`：Postgres/Alembic/job/outbox/identity。
- `map_core/tests/golden/`：脱敏运行轨迹和 replay adapter。
- `map_core/tests/security/`：tool approval/evaluation side-effect denial/evidence redaction。
- `map-business-frontend/src/test/`：MSW server、SSE fixtures、render helpers。
- `tests/e2e/`：建议 Playwright；Compose/kind profile 启动最小全链路。
- `scripts/verify_audit_chain.py`、`scripts/verify_migration.py`、`scripts/run_golden_eval.py`、`scripts/export_version_manifest.py`。

### 10.3 关键不变量（任何版本都不得破坏）

1. 一个 request 的 BFF/core/Mongo/OTel `request_id` 一致；一个 conversation 的 `session_id` 稳定。
2. 未授权 workspace 资源永远不进入查询结果，即使随后 service 层再过滤也不算合格。
3. 未批准副作用工具调用次数为 0；批准 grant 对相同 args 只能消费一次。
4. published/evaluated dataset/config/asset version 不可原地修改。
5. 评测 replay 不访问真实副作用工具。
6. audit applied/failed 都存在，且 actor 不能由业务 payload 伪造。
7. 无 evidence 不得在 UI 构造来源；无 price 不得按 0 成本；无 metric 数据不得报 100% SLA。
8. 客户端断开不改变 async task 的执行状态；客户端重复 event 不重复拼接内容。
9. 删除请求完成后所有面向用户/管理员的查询和导出都找不到被删原文。
10. OTel/Mongo/notification/export 任何出口不包含密钥字段。

### 10.4 PR 级 Definition of Done

每个工作包 PR 必须同时给出：

- 对应工作包 ID、范围内/范围外说明、依赖提交；
- 设计/SPEC/OpenAPI 变更；
- migration 与 rollback/forward-fix 说明；
- 权限矩阵和数据隔离说明；
- 幂等键、乐观锁、重试、副作用语义；
- happy path + 至少两个失败/竞态测试；
- 运行过的精确命令和结果；
- 观测字段/metric/audit 事件；
- feature flag、灰度、回滚步骤；
- 已知限制和后续卡号。

只有代码和单测、没有契约/迁移/权限/回滚说明的 PR 不满足完成标准。

## 11. 发布、灰度与回滚

### 11.1 Feature flags

建议统一由版本化配置管理，至少包含：

- `conversation_persistence_enabled`
- `feedback_enabled`
- `evidence_contract_v1_enabled`
- `decision_policy_enabled`
- `evaluation_publish_gate_enforced`
- `async_task_enabled`
- `hitl_enabled`
- `im_connector_enabled`
- `subscription_enabled`
- `cost_ledger_enabled`
- `postgres_config_repository_enabled`
- `durable_runtime_events_enabled`

Flag 规则：默认值按环境写清；记录在 request/config snapshot；禁用只能回退功能入口，不能删除已产生数据；安全门禁/HITL 在已发布为强制后不得被普通 workspace admin 关闭。

### 11.2 Expand/contract 数据迁移

1. expand：先加 nullable/兼容字段和表，部署可同时读旧结构的代码。
2. backfill：幂等、分批、可观察、可暂停；记录进度和校验 hash/count。
3. switch：feature flag/shadow compare 后切读。
4. contract：至少跨一个稳定版本再删旧字段/路径；删除前确认所有副本和 worker 已升级。

禁止在同一部署中“先删旧字段，再指望所有应用同时切换”。

### 11.3 各版本回滚边界

- R1：新表/字段只扩展；关闭 UI/feature flags 可回旧 chat。已写反馈/审计/评测不得丢弃。发布 gate 出故障可由 break-glass，不可直接删检查。
- R2：任务/审批含副作用状态，不能通过 DB 回滚让 terminal 变 queued；应用回滚前暂停领取、清点 running/awaiting tasks；通知只重试 delivery。
- R3：AdminState 切库回滚必须导出 DB 新变更并校验；K8s rollback 不自动 downgrade migration；workspace/lifecycle 数据不可退回无 scope 旧代码直接运行。

### 12.1 必须由人确认的决策门

### 12.2 最高风险与停止条件

| 风险 | 监测 | 必须停止/回退的条件 |
| --- | --- | --- |
| AgentScope 语义漂移 | golden eval、SSE contract、tool governance | critical regression 或副作用重复 |

| 事件可靠性倒退 | outbox backlog、Mongo counts | request/tool/usage 关键事件不可恢复丢失 |

## 13. 明确不做与边界外事项

本阶段禁止 coding agent 顺手加入：

1. 自训模型、微调平台、训练数据流水线。
2. 通用低代码/BPM 画布；心流只提供执行图只读可视化、节点策略和人工裁决。
3. 公有云 SaaS 自助注册、外部租户计费、独立域名、跨客户运营后台。
4. iOS/Android 原生 App；只做响应式 Web + 单一企业 IM。
5. 同时实现钉钉和企微；R2 只做选定渠道，另一个只保留 SPI。
6. R2 硬预算拒绝、自动采购额度；只做软预算和告警。
7. R3 v1 的 LDAP 密码直连、SCIM server；企业网关/trusted header 可作为兼容入口。
8. 在评测失败后自动修改 prompt 并发布；评测只提供证据和门禁。
9. 自动把 AgentCase/repair candidate 直发生产；必须人工审核、评测、灰度。
10. 把完整 chain-of-thought 暴露给用户；“思考过程”页面只展示可审计的执行步骤、工具和证据摘要。
11. 把 PostgreSQL job queue 抽象提前替换成 Kafka/Redis，除非 R2/R3 压测证明不达标并有独立 ADR。
12. 默认保存完整 SQL 结果、KB 文档、工具原始 payload 或 OIDC token。

## 15. 最终交付判定

本计划的完成不是“所有页面出现入口”，而是以下闭环都真实成立：

1. 用户答案能追到权限过滤后的证据；错误能反馈并转成不可变评测用例；配置发布必须通过与候选 hash 一致的评测。
2. 会话、任务、审批、通知、订阅使用同一 principal/workspace/ID/作业框架；断线和进程重启不会绕过审批或重复副作用。
3. Agent/Skill/Scenario/AgentCase 有统一版本和生命周期，草稿不能直接进入生产，灰度可观察、可停止、可回退。
4. 配置和产品状态进入 PostgreSQL 后可多副本运行；执行事件可恢复投影；Helm/CI 能复现部署版本。
5. 身份、空间隔离、脱敏、保留、删除、审计、SLA 均有自动化证据，并通过至少一次内部安全评审。

只有达到各版本“总验收”且没有遗留 P0/P1，才可将对应版本标记为完成。
