# MAP 企业级多智能体平台 —— 产品欠缺项评估与下一阶段产品规划

> 版本：v1.0（2026-08-07）
> 视角：产品经理 + 业务使用人员（管理员 / 普通用户 / 安全审计员）
> 输入：repowiki 全量文档、SPEC/、TODO/心流模式技术方案、管理端功能清单、可观测性系统现状

## 1. 产品现状盘点（我们已经有什么）

| 能力域 | 现状 | 成熟度 |
| --- | --- | --- |
| 对话执行 | 全域模式（场景识别→多 Agent 并发→汇总）+ 心流模式（执行图/证据/修复/回退） | ★★★★ |
| 动态治理 | 管理端 15+ 配置面板：模型中心、Agent、MCP、心流策略、Scenario/Skill Hub、词库、RBAC 等，热更新无需重启 | ★★★★ |
| 安全执行 | 工具预挂载 + 运行时二次鉴权，多维度（用户/租户/场景/权限范围）控制 | ★★★☆ |
| 可观测 | 请求/Agent/工具三层事件入库，链路树可视化、错误聚类、Friday 诊断 | ★★★ |
| 交付形态 | Docker Compose 单机编排，四服务 + 双数据库 | ★★ |

**一句话判断：MAP 的"执行与治理内核"已达到企业试点水平，但围绕内核的"效果闭环、协作流程、交付与合规外围"存在系统性缺失——这正是从"能用的平台"到"企业愿意规模化采购/推广的产品"之间的差距。**

## 2. 欠缺项评估（我们还缺什么）

按"业务价值 × 缺失严重度"排序，分为四层。

### 2.1 效果与信任层（最致命：用户为什么信任答案？）

| # | 欠缺项 | 业务痛点场景 |
| --- | --- | --- |
| E1 | **无评测体系（Evaluation）**：没有测试集管理、回归评测、A/B 对比。改一句提示词、换一个模型，效果变好还是变坏全凭手感 | 管理员调整了问数 Agent 的提示词，第二天业务方投诉数据口径答错了——没人知道是这次改动导致的 |
| E2 | **无用户反馈闭环**：对话界面无点赞/点踩/纠错入口，反馈无法沉淀为坏例集或训练/优化素材 | 用户发现答案错误只能截图发群里，平台侧无感知、无统计 |
| E3 | **无答案溯源/引用**：回答未强制标注证据来源（哪个知识库分片、哪条 SQL、哪次工具调用），心流模式已有 evidence contract 但未产品化到用户界面 | 财务同事拿到一个数字，不敢直接写进汇报——无法核实出处 |
| E4 | **无置信度与拒答策略**：场景识别不确定、工具失败时缺少产品化的"我不确定/建议人工"表达 | 模型在低置信场景硬答，一次错误答案摧毁一个部门的信任 |
| E5 | **提示词/配置变更无评测门禁**：Master Agent 有版本管理（发布/回滚），但发布前无强制回归评测 | "发布"按钮点下去等于直接上生产 |

### 2.2 用户体验层（业务用户日常用得爽吗？）

| # | 欠缺项 | 业务痛点场景 |
| --- | --- | --- |
| U1 | **会话产品化不足**：缺少会话历史列表/搜索/收藏/分享、常用问题模板、追问建议 | 用户上周查过的分析结果找不回来，只能重新问 |
| U2 | **长任务体验缺失**：心流模式多节点执行可能数分钟，缺少任务进度页、后台运行、完成通知；一切都挂在一个 SSE 连接上，刷新即丢 | 用户发起一个跨域分析后不敢关页面 |
| U3 | **人在环路（HITL）缺失**：高风险操作（写库、发送、审批类工具）无"执行前确认"交互；心流修复路径无人工介入点 | 业务方明确要求"涉及资金数据的查询要人工确认"，当前无法满足 |
| U4 | **多端与嵌入能力弱**：仅 Web 控制台，无企业 IM（钉钉/企微/飞书）机器人接入、无 iframe/SDK 嵌入方案 | 业务方希望在自己的系统里嵌一个问数入口，目前只能跳转 |
| U5 | **结果消费形态单一**：附件/图表能力已有，但缺少"结果转报表/定时订阅/推送"的持续消费方式 | 用户每天早上手动问同一个问题 |

### 2.3 治理与协作层（管理员和组织如何规模化运营？）

| # | 欠缺项 | 业务痛点场景 |
| --- | --- | --- |
| G1 | **配置无审计与审批流**：AdminState 是单 JSON 文件，谁改了什么、何时改的、能否双人复核——全无记录 | 安全审计要求"所有权限变更可追溯"，当前无法通过审计 |
| G2 | **无多租户/多空间**：Agent、知识库、词库、策略全局共享，无法按部门/项目隔离运营 | 两个事业部都要用平台，配置互相踩踏 |
| G3 | **Agent 资产无生命周期管理**：Agent/Skill/Scenario Pack 缺少草稿→测试→灰度→发布→下线的状态机（Master Agent 有雏形，未推广到全部资产） | 新 Agent 直接对全员可见，出问题影响面不可控 |
| G4 | **成本治理缺失**：token 用量有记录但无预算、配额、按部门分摊账单、成本告警 | 月底发现某个 Agent 烧了 80% 的模型预算，无人预警 |
| G5 | **经验沉淀未闭环**：TODO 中 Phase 4（AgentCase 抽取→候选 hyperedge→人工审核→灰度）尚未落地，好的执行轨迹无法复用 | 同类问题每次都重新走一遍试错路径 |

### 2.4 企业交付层（IT/安全部门放行吗？）

| # | 欠缺项 | 业务痛点场景 |
| --- | --- | --- |
| D1 | **无企业身份集成**：自建 RBAC，未对接 SSO/OIDC/LDAP | IT 部门不允许独立账号体系上生产 |
| D2 | **高可用与扩展性不足**：单机 compose、AdminState 文件存储、事件有界队列可丢；无 K8s 交付物、无水平扩展方案 | 采购评审第一个问题："支持双活吗？" |
| D3 | **无 CI/CD 与版本化发布**：构建部署纯手工 compose，配置与代码版本无对应关系 | 升级出问题无法快速定位"这个环境到底跑的什么版本" |
| D4 | **数据合规能力薄弱**：日志/事件中的敏感数据脱敏不系统，无数据保留策略、无删除权（GDPR 类）支持 | 安全评估卡在"用户对话数据保留多久、能不能删" |
| D5 | **告警与 SLA 缺失**：观测系统只能"看"，不能"叫"——无错误率/延迟阈值告警，无 SLA 报表 | 服务半夜挂了，早上业务方先发现 |

## 3. 下一阶段产品规划

### 3.1 产品主题与北极星

**主题：从"可运行的多智能体平台"进化为"可信、可运营、可交付的企业智能体产品"。**

北极星指标：**周活跃提问用户数 × 答案采纳率**（采纳 = 点赞/引用/未追问纠错）。

配套护栏指标：答案错误反馈率、P95 响应时间、单次请求平均成本、配置变更回滚率。

### 3.2 版本节奏（三个迭代，约 2 个季度）

> 说明：R1 与《AgentScope 2.0 改造计划》并行推进，评测体系（R1）恰好为引擎切换提供效果回归护栏，二者互为支撑。

#### R1「可信版」（第 1~6 周）—— 解决"敢不敢信"

| 特性 | 覆盖欠缺项 | 关键需求点 |
| --- | --- | --- |
| 评测中心 v1 | E1、E5 | 测试集管理（按场景/Agent 维度）；一键回归评测（复用黄金轨迹）；提示词/模型变更发布前强制跑评测并出对比报告 |
| 用户反馈闭环 v1 | E2 | 对话消息级点赞/点踩 + 纠错原因；反馈自动聚合到观测系统坏例列表；管理员可将坏例一键转为测试集用例 |
| 答案溯源 v1 | E3 | 回答尾部展示证据卡片（知识库片段/SQL/工具调用摘要），点击展开调用树对应节点；心流 evidence contract 结果前端可视化 |
| 拒答与置信策略 | E4 | 场景识别低置信 → 澄清追问话术；工具连续失败 → 明确"无法回答 + 原因 + 建议"；策略在管理端可配 |
| 配置审计日志 | G1 | AdminState 所有写操作记录操作人/时间/diff；审计页面可检索 |

R1 验收：答案可溯源比例 ≥80%；任何提示词变更均有评测报告；反馈率（有反馈的会话占比）≥15%。

#### R2「好用版」（第 7~14 周）—— 解决"愿不愿常用"

| 特性 | 覆盖欠缺项 | 关键需求点 |
| --- | --- | --- |
| 会话中心 | U1 | 历史会话列表/搜索/重命名/收藏；会话分享（链接 + 权限）；常用问题模板与首页推荐打通 |
| 异步任务与通知 | U2 | 心流长任务转后台运行；任务中心页（进度=执行图节点状态）；完成后站内 + IM 通知；断线重连恢复流 |
| 人在环路 v1 | U3 | 工具级"需确认"标记（管理端配置）；执行到该工具时暂停并向用户/审批人推送确认卡片；心流 uncertain 节点支持人工裁决后继续 |
| 企业 IM 接入 | U4 | 钉钉/企微机器人（二选一先行）：@机器人提问、卡片式答案 + 溯源链接、长任务完成推送 |
| 定时订阅 v1 | U5 | 将任意问题存为订阅（cron），结果推送 IM/邮件；订阅管理页 |
| 成本看板 v1 | G4 | 按 Agent/用户/部门的 token 成本报表；月度预算与 80% 阈值告警 |

R2 验收：周活跃提问用户数环比 +50%；IM 渠道提问占比 ≥30%；长任务完成率（不因断连丢失）≥99%。

#### R3「规模版」（第 15~24 周）—— 解决"能不能全公司推"

| 特性 | 覆盖欠缺项 | 关键需求点 |
| --- | --- | --- |
| 工作空间（多租户）v1 | G2 | 空间 = 独立的 Agent/知识库/词库/策略/成员集合；空间级管理员；跨空间共享需显式发布 |
| 资产生命周期 | G3、G5 | Agent/Skill/Scenario Pack 统一状态机：草稿→测试→灰度（按人群比例）→发布→下线；落地 AgentCase 经验沉淀 Phase 4（trace 抽取→候选策略→人工审核→灰度） |
| 企业身份集成 | D1 | OIDC/SSO 对接；组织架构同步（部门→空间/角色映射） |
| 高可用交付 | D2、D3 | AdminState 迁移 PostgreSQL（含版本化）；Helm Chart / K8s 交付物；CI/CD 流水线（构建→测试→评测门禁→部署）；事件队列可靠性加固（落盘缓冲或消息队列） |
| 告警与 SLA | D5 | 基于 OTel Metrics 的错误率/延迟/成本告警（对接 IM）；月度 SLA 报表 |
| 数据合规 v1 | D4 | 对话数据保留策略（按空间配置 TTL）；用户数据删除接口；脱敏规则统一治理页 |

R3 验收：≥3 个部门以独立空间运营；发布流水线含评测门禁；通过一次内部安全评审。

### 3.3 明确不做（本阶段）

1. **自训模型/微调平台**——继续走外部模型 + 提示词/评测优化路线，成本收益比更高。
2. **通用低代码流程画布**——心流模式的执行图由 Scenario Pack 驱动即可，避免做成第二个 BPM；仅提供执行图"只读可视化 + 节点级配置"。
3. **公有云 SaaS 多租户**——目标客群是私有化企业部署，R3 的工作空间仅解决企业内部多部门隔离。
4. **移动原生 App**——IM 机器人 + 响应式 Web 已覆盖移动场景。

### 3.4 风险与依赖

| 风险 | 缓解 |
| --- | --- |
| R1 评测中心依赖标注人力，测试集冷启动慢 | 从用户点踩坏例自动转化 + 从历史 request_records 抽样，降低人工成本 |
| R2 IM 接入受企业 IT 审批周期影响 | 提前一个迭代发起对接申请；先做 webhook 极简版 |
| R3 AdminState 迁库涉及 BFF 大改，与引擎改造撞车 | 排期错峰：引擎改造 P4 收尾后再启动迁库 |
| 人在环路改变执行链路，可能与 AgentScope 引擎切换互相干扰 | HITL 设计基于"工具执行前暂停"这一引擎无关的切面（ToolAdapter/Executor 层），两条线解耦 |

### 3.5 需要决策的开放问题

1. R2 的 IM 渠道先做钉钉还是企微？（取决于目标客户 IT 环境）
2. 评测中心的评分方式：纯 LLM-as-Judge、规则断言、还是人工抽检混合？建议 R1 先"规则断言 + LLM Judge"，人工抽检作为校准。
3. 工作空间与现有 RBAC 的关系：空间内独立角色，还是全局角色 + 空间资源范围？建议后者，改造量更小。
