## 5. 剩余问题与整改标准

## R7-P2-01：工作树侧 rename（`XY=" R"`）仍可绕过 clean-product final gate

### 证据位置

- `scripts/source_control.py:85`：parser 以 `"R" in xy` 识别任一列 rename；
- `scripts/source_control.py:107-108`：分类却仅判断 `xy[0] == "R"`；
- `map-business-backend/tests/test_source_control_snapshot.py:125-208`：所有真实 rename 通过 `git mv` 产生 `R `，缺少 ` R`；
- gate 和 E2E 都消费同一个错误的 `affected_paths`，因此会一致放行。

### 根因

实现把“rename 的语义”错误等同于“索引状态 X 是 R”。Git porcelain 的 rename 可出现在 X 或 Y；只要 `xy` 任一列为 `R`，origin 就表示被重命名的旧路径，必须参与受影响路径分类。当前 parser 与 classifier 对同一 `XY` 的语义判断不一致。

### 风险

- 产品文件可以在 dirty 工作树中移入 TODO/Markdown 后被标记为 docs-only；
- `RELEASE_GATE_FINAL=1` 会在产品删除/移动尚未提交时继续跑完并给出 PASS；
- E2E artifact 会错误记录 `dirty_product=[]`，SHA/tree 又不包含 dirty 产品变化，从而不能自证实际被测内容；
- 这是证据链 fail-open，不代表已经通过的运行时业务场景回退，但违反 final gate 的核心不变量。

### 整改方向

1. rename 判定必须覆盖 `XY` 两列。最小正确语义是：当 `"R" in entry["xy"]` 且存在 `orig_path` 时，destination 和 origin 都进入 `affected_paths`；
2. copy 继续与 rename 分开：`"C" in xy` 时 origin 只保留审计，不作为被删除路径；
3. 不要在 gate/E2E 再增加补丁式分类；继续只修共享 `source_control.py`，由同一 `affected_paths` 驱动所有消费者；
4. 对异常组合或缺失 origin 保持 fail-closed；parser 已有 missing-origin 校验，不得弱化；
5. 文档注释和质量记录要明确 `R ` 与 ` R` 都属于 rename，不再把 staged `git mv` 等同于完整 rename 状态空间。

### 整改验收标准

- 在真实临时 Git 仓库固化以下两个 product -> docs 重放：
  - `git mv app.py TODO/app.py.md`，产生 `R `，CLI exit 2；
  - `mv app.py TODO/app.py.md && git add -N TODO/app.py.md`，产生 ` R`，CLI exit 2；
- 四象限 rename 必须对 `R ` 和 ` R` 各执行一套，至少 8 个真实仓库用例：product->product、product->docs、docs->product 前三类均 product dirty，只有 docs->docs 可 docs-only；
- 两种列位置下 `affected_paths` 都必须精确包含 destination 与 origin，去重和排序稳定；
- copy 在 `C ` 与可构造的工作树列形态下仍只按 destination 分类，origin 继续保留在 entry；
- 现有 15 项测试全部继续通过；新增失败复现先红后绿，最终 snapshot 测试总集全绿；
- 用同一临时仓库分别调用 shared snapshot、final gate 的 source precheck 和 E2E source precheck，三者输出的 affected/product 分类一致；
- `--require-clean-product` 对任一 product-affecting rename 必须在任何后续测试前非零退出。

## R7-P2-02：release gate 的 diff-check 不检查已提交范围，final artifact 也未携带 baseline

### 证据位置

- `scripts/release_gate.sh:47`：读取 `GATE_BASELINE_SHA`；
- `scripts/release_gate.sh:86-88`：只打印 baseline；
- `scripts/release_gate.sh:130`：实际只执行 `git diff --check`；
- `tmp/gate-logs/gate-summary.json`：`source_control.baseline_sha=null`，diff command=`git diff --check`、exit 0；
- `map-business-backend/QUALITY_FIX_RECORD.md:544`：当前 committed range 存在 `new blank line at EOF`；
- `git diff --check 49e6295..HEAD` 与 `git diff --check 7d2b813..HEAD` 均 exit 2。

### 根因

无参数 `git diff --check` 只检查工作树相对索引的未提交差异。工作树干净时，它无法检查已经进入 HEAD 的 trailing whitespace 或 blank-at-EOF。虽然 gate 接收 baseline，但 baseline 只是 artifact 元数据，没有驱动校验命令；本次 final run 甚至没有设置 baseline，因此 gate 的“diff-check PASS”与整体提交质量没有等价关系。

### 风险

- 已提交 whitespace 缺陷可以在完全 clean 的工作树上稳定通过 release gate；
- artifact 显示 diff-check exit 0，容易被误解为整改范围 `baseline..HEAD` 已检查；
- 后续提交若引入真实 patch 格式问题，最终门禁仍可能假绿；
- 当前仓库已经出现真实反例，不再只是理论风险。

### 整改方向

1. 立即删除 `QUALITY_FIX_RECORD.md` 末尾多余空行，使当前目标范围 `git diff --check` 归零；
2. final 模式必须要求显式有效的 `GATE_BASELINE_SHA`，缺失、无法解析或不是 HEAD 祖先时 fail-closed；
3. gate 至少拆成两个可审计步骤：
   - working-tree check：`git diff --check`；
   - committed-range check：`git diff --check "$GATE_BASELINE_SHA"..HEAD`；
4. 两个步骤的完整命令、exit code、log hash 和 baseline 必须进入 `gate-summary.json`；
5. 非 final 本地模式如允许省略 baseline，必须明确记录 committed-range step 为 skipped 及原因，不能伪装成已通过；final 模式不得 skip；
6. 建议用 `git merge-base --is-ancestor "$GATE_BASELINE_SHA" HEAD` 固化范围方向，避免错误 baseline 产生误导性空 diff。

### 整改验收标准

- `git diff --check 7d2b81342ad96a612ac86091673506e203075c5d..HEAD` exit 0；
- 新增真实临时仓库回归：baseline 后提交一个带 trailing whitespace 或 blank-at-EOF 的文件，保持工作树 clean；working-tree check 可为 0，但 committed-range step 必须非零并使 final gate 失败；
- 修复该临时提交后 committed-range step 必须恢复为 0；
- `RELEASE_GATE_FINAL=1` 且未设置 baseline、baseline 不存在、baseline 不是祖先时分别非零退出；
- 最终执行必须显式使用：

```bash
RELEASE_GATE_FINAL=1 \
GATE_BASELINE_SHA=7d2b81342ad96a612ac86091673506e203075c5d \
bash scripts/release_gate.sh
```

- 最终 artifact 必须记录 `baseline_sha=7d2b813...`，working-tree 与 committed-range 两个 diff step 均 exit 0；
- 最终 artifact 的 `git_sha`/`git_tree` 必须与交付时 `git rev-parse HEAD`/`HEAD^{tree}` 一致，之后不得再修改或提交产品、测试、gate、质量记录文件。

## 7. 第八轮最小验收门槛

第八轮无需重新展开所有历史整改，只需逐项满足：

## 8. 最终判定

第六轮修复确实关闭了 staged `git mv` 的原始反例，且没有引入运行时回归；现有 final gate、PR E2E 和历史 full E2E 证据本身均真实存在并可复核。effect、worker、身份、会话、反馈、审计、browser 和供应链等已关闭项继续有效，P0/P1 保持为零。

但是，工作树侧合法 rename 状态 `XY=" R"` 仍能让产品文件移动到文档目录后被误判为 docs-only，说明 R6-P2-01 只修复了一半状态空间。同时 release gate 没有使用 baseline 检查已提交范围，当前仓库已经以 `QUALITY_FIX_RECORD.md` EOF 空行证明该步骤会假绿。

因此第七轮最终结论为：**业务回归通过，证据链整改暂不完全通过；剩余 2 个 P2。完成 R7-P2-01 与 R7-P2-02、建立失败复现、在同一不可变 HEAD 上重建带 baseline 的 final gate 和 PR E2E 证据后，方可进入最终关闭审查。**
